Lección 01 · Proyecto 00-foundations

El primer apply que no es de juguete

Antes de desplegar nada en AWS montas la red de seguridad. Hoy creas un presupuesto con alarma —con Terraform, no a mano— y abres el fichero de state para ver qué guarda Terraform realmente.

Tiempo 35 min Coste 0,00 USD Terraform provider · resource · plan/apply · state AWS Budgets

Por qué esto y no un bucket S3

En el proyecto 04-vpc-three-tier vas a levantar un NAT Gateway, un ALB y una base de datos RDS. Esas tres cosas cobran por hora estén o no en uso, y la primera vez que a alguien se le olvida un destroy un viernes, el lunes tiene una factura de 40 USD. El presupuesto con alarma es el cinturón de seguridad de todo el curso, así que va primero.

Pero hay una segunda razón, y es la que te sirve en una entrevista: este es literalmente el primer commit de cualquier repositorio de infraestructura real. Nadie empieza un repo de Terraform creando un bucket. Se empieza estableciendo los límites de la cuenta. Que tu repo empiece así dice más de ti que cualquier módulo sofisticado que venga después.

Lo que vamos a hacer mal a propósito

Hoy vas a ejecutar Terraform con las credenciales root de tu cuenta. Eso está mal y lo sabemos. Lo hacemos porque crear el usuario IAM que usaremos a partir de mañana requiere permisos que solo root tiene de entrada. Root hará exactamente dos cosas en todo el curso: este presupuesto, y crear ese usuario en la lección 03. Después, nunca más.

El modelo mental: tres realidades, no dos

Casi todo el mundo que viene de tutoriales cree que Terraform compara tu código contra AWS. No es así, y esa confusión es la raíz de la mitad de los problemas que verás. Terraform maneja tres representaciones de tu infraestructura:

Esto explica cosas que de otro modo parecen magia negra:

  • Si borras un recurso a mano en la consola de AWS, el siguiente plan lo detecta en el paso ① y te propone recrearlo. El state se ha desincronizado de la realidad, y Terraform lo corrige.
  • Si borras el fichero de state, Terraform olvida que esos recursos existen y te propone crearlos otra vez — aunque ya estén ahí. Por eso el state es el activo más valioso de tu infraestructura, y por eso en la lección 02 lo sacaremos de tu portátil a un bucket S3.
  • Si alguien modifica el recurso a mano (le cambia una etiqueta), el paso ① lo ve y el paso ② te propone revertirlo. Eso se llama drift, y es la palabra que te van a preguntar en una entrevista.
Vocabulario que se usa de verdad

Provider: un plugin que traduce tu HCL a llamadas de la API de un servicio. hashicorp/aws es un binario que Terraform descarga y que sabe hablar con AWS.
Resource: una cosa que Terraform crea y cuya vida gestiona.
Drift: la diferencia entre el state y la realidad.
Todos estos entran en el glosario.

Manos a la obra

  1. Recupera tus credenciales y comprueba en qué cuenta estás

    Ahora mismo no tienes sesión activa. Y antes de crear nada, la regla de oro: nunca ejecutes Terraform sin haber comprobado en qué cuenta AWS estás.

    aws login --profile personal
aws sts get-caller-identity --profile personal

    Tienes que ver la cuenta 999999999999. Si ves 111111111111, estás en el perfil equivocado — esa es la cuenta dara.

    Ahora exporta el perfil para toda la sesión de terminal, para no repetir --profile ni escribirlo dentro del código:

    export AWS_PROFILE=personal
    Por qué por variable de entorno y no en el .tf

    Podrías escribir profile = "personal" dentro del bloque provider. No lo hagas. Ese nombre de perfil solo existe en tu portátil: en GitHub Actions, en el portátil de un compañero o en un servidor de CI no significa nada, y el código deja de ser portable. La configuración describe la infraestructura; las credenciales vienen del entorno. Esa separación es un criterio real de revisión de código.

  2. Crea el proyecto

    cd ~/Dev/terraform
mkdir -p projects/00-foundations
cd projects/00-foundations

  3. Declara la versión de Terraform y del provider

    Escribe este fichero. Sí, a mano — teclear HCL es parte del ejercicio.

    projects/00-foundations/versions.tfnuevo
    terraform {
  required_version = ">= 1.9"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"

  # Se aplican automáticamente a TODO recurso que soporte etiquetas.
  default_tags {
    tags = {
      Project   = "terraform-course"
      Stack     = "00-foundations"
      ManagedBy = "terraform"
    }
  }
}
    Por qué default_tags importa más de lo que parece

    La etiqueta ManagedBy = "terraform" te permite responder en cualquier momento a la pregunta «¿qué hay en mi cuenta que no gestiona Terraform?». En una cuenta real esa es la pregunta que separa una infraestructura sana de un vertedero. También es como localizas recursos huérfanos que se te olvidó destruir — y por tanto, como controlas la factura.

    ~> 6.0 significa «cualquier 6.x, pero nunca 7.0». La versión mayor de un provider puede romper tu código sin avisar; esto te protege. Hoy la última es la 6.61.0.

  4. Inicializa y mira lo que ha pasado

    terraform init

    Ahora inspecciona lo que ha aparecido en el directorio. Esto no es curiosidad ociosa: saber qué es cada fichero es la mitad de entender Terraform.

    ls -a
du -sh .terraform
cat .terraform.lock.hcl
    FicheroQué es¿A git?
    .terraform/El binario del provider descargado (~600 MB). Caché local, recreable.No
    .terraform.lock.hclLa versión exacta del provider y sus hashes. Garantiza que tú y tu CI usáis el mismo binario.Sí, siempre

    El lock file es el equivalente de package-lock.json. La gente lo ignora en .gitignore por error constantemente, y luego su CI usa una versión distinta del provider que la suya y aparecen diffs fantasma. (docs)

  5. Escribe el presupuesto

    Esto es lo que has venido a construir. Fíjate en var.alert_email: tu correo no se escribe en el código, porque este repo va a ser público.

    projects/00-foundations/budget.tfnuevo
    variable "alert_email" {
  description = "Correo que recibe las alarmas de gasto."
  type        = string
}

variable "monthly_budget_usd" {
  description = "Techo de gasto mensual en dólares."
  type        = number
  default     = 30
}

resource "aws_budgets_budget" "monthly" {
  name         = "curso-terraform-mensual"
  budget_type  = "COST"
  time_unit    = "MONTHLY"
  limit_amount = tostring(var.monthly_budget_usd)
  limit_unit   = "USD"

  # AVISO TEMPRANO: al 50% del gasto real ya consumido.
  notification {
    notification_type          = "ACTUAL"
    comparison_operator        = "GREATER_THAN"
    threshold                  = 50
    threshold_type             = "PERCENTAGE"
    subscriber_email_addresses = [var.alert_email]
  }

  # AVISO REAL: AWS proyecta que a fin de mes te pasarás del 100%.
  # Este es el que de verdad te salva: avisa ANTES de gastar.
  notification {
    notification_type          = "FORECASTED"
    comparison_operator        = "GREATER_THAN"
    threshold                  = 100
    threshold_type             = "PERCENTAGE"
    subscriber_email_addresses = [var.alert_email]
  }
}

output "budget_console_url" {
  description = "Dónde ver el presupuesto en la consola de AWS."
  value       = "https://console.aws.amazon.com/billing/home#/budgets"
}
    ACTUAL vs FORECASTED

    Una alarma sobre gasto ACTUAL te avisa cuando ya has gastado el dinero: llega tarde por definición. FORECASTED usa la proyección de AWS a fin de mes, así que un NAT Gateway olvidado un martes te avisa el martes, no el día 28. En una cuenta de aprendizaje la alarma de proyección es la que importa. Es también la respuesta que quieren oír si te preguntan por control de costes.

    Ahora el fichero con tu correo, que no va a git:

    projects/00-foundations/terraform.tfvarsnuevo · fuera de git
    alert_email        = "tu-correo@example.com"
monthly_budget_usd = 30

    Terraform carga terraform.tfvars automáticamente, sin pasar ningún flag.

  6. Lee el plan antes de aplicarlo

    terraform plan

    Antes de seguir, léelo de verdad. Busca estas cuatro cosas:

    • La línea de resumen: Plan: 1 to add, 0 to change, 0 to destroy.
    • El símbolo + delante del recurso — significa «crear».
    • Los valores (known after apply): cosas que AWS decide, no tú (ARNs, IDs).
    • Tus default_tags, que aparecen aunque no las escribieras en el recurso.
    El hábito que separa a un profesional

    Leer el plan no es un trámite antes de teclear yes. En un equipo real el plan es el artefacto de revisión: se pega en el pull request y un compañero lo aprueba. Los símbolos que verás durante el curso son + crear, - destruir, ~ modificar en sitio, y -/+ destruir y recrear. Ese último es el peligroso: si sale al lado de tu base de datos, para y piensa.

  7. Aplica

    terraform apply

    Terraform vuelve a calcular el plan, te lo enseña y te pide confirmación. Escribe yes. Debería tardar un par de segundos.

    Verifícalo desde fuera de Terraform — otro hábito que vale la pena coger:

    aws budgets describe-budgets --account-id 999999999999 \
  --query 'Budgets[].{Nombre:BudgetName,Limite:BudgetLimit.Amount}' --output table
    Corrección — esto lo dije mal

    Aquí escribí originalmente que AWS te enviaría un correo de confirmación de suscripción. No cuentes con ello: con subscriber_email_addresses a secas, AWS gestiona la suscripción internamente y el comportamiento no es observable desde tu cuenta.

    Peor aún: la alarma FORECASTED que acabas de crear no puede dispararse hasta que tu cuenta acumule unas 5 semanas de historial de uso (AWS Budgets — Best practices). Está creada, y está inerte.

    Las dos cosas se arreglan y se prueban en la lección 02. Si quieres el detalle completo del servicio —tipos, límites, coste, cuándo no usarlo— está en reference/aws-budgets.html.

  8. Abre el state y mira qué guarda

    Este es el paso que casi nadie da, y el que más te va a servir.

    ls -la terraform.tfstate
cat terraform.tfstate | head -40

    Fíjate en la estructura: un JSON con "version", "serial", "lineage" y una lista de "resources". Cada recurso tiene su dirección (aws_budgets_budget.monthly) y sus attributes — todos los atributos, incluidos los que AWS rellenó.

    Compáralo con la vista que da Terraform:

    terraform state list
terraform state show aws_budgets_budget.monthly
    El state guarda secretos en texto plano

    Aquí solo hay un correo. Pero cuando en el proyecto 04 crees una base de datos RDS, la contraseña quedará escrita en claro dentro de este JSON. Terraform no cifra el state, y no hay opción para que lo haga. (docs oficiales)

    De ahí salen dos reglas que no se negocian: el state nunca va a git, y el state vive en un bucket S3 cifrado y con acceso restringido. Lo segundo es la lección 02.

    En la raíz del repositorio ya te he dejado el .gitignore. Ábrelo y comprueba que entiendes cada línea — esto es lo que impide que ese JSON acabe publicado en GitHub:

    ~/Dev/terraform/.gitignoreya creado
    .terraform/
*.tfstate
*.tfstate.*
*.tfvars
!*.tfvars.example
crash.log
.terraform.tfstate.lock.info

    Nota lo que no está en esa lista: .terraform.lock.hcl. Ese sí va a git.

  9. Entiende destroy sin ejecutarlo

    El presupuesto se queda. Es lo único de todo el curso que no se destruye — cuesta cero y te protege. Pero quiero que veas qué haría destroy, sin hacerlo:

    terraform plan -destroy

    Sale Plan: 0 to add, 0 to change, 1 to destroy. y cada atributo precedido de -. Es un plan normal, solo que calculado contra un objetivo vacío. No ejecutes terraform destroy.

Responde sin volver a subir. Fallar aquí es útil: es lo que hace que mañana lo recuerdes.

Pregunta 1 de 3

Borras un recurso a mano desde la consola de AWS. ¿Qué ve el siguiente terraform plan?

Pregunta 2 de 3

De estos cuatro ficheros, ¿cuál es el único que sí debe estar en git?

Pregunta 3 de 3

Quieres que te avisen antes de gastar de más, no después. ¿Qué alarma configuras?

Explícalo con tus palabras antes de abrir Di en voz alta, sin mirar: ¿por qué el state es el activo más valioso de una infraestructura Terraform?

Porque el state es el único sitio donde vive la correspondencia entre tu código y los recursos reales de AWS. Tu código dice «quiero un presupuesto llamado monthly»; AWS tiene un presupuesto con un identificador. Solo el state sabe que son el mismo.

Si lo pierdes, Terraform no puede saber qué recursos ya gestiona. Vuelve a proponer crearlo todo, y el apply falla con «ya existe» — o peor, crea duplicados. Recuperarse de eso significa terraform import recurso por recurso, a mano.

De ahí salen las tres propiedades que le exigimos: durable (no en tu portátil), bloqueable (que dos personas no lo escriban a la vez) y versionado (poder volver a la versión de ayer). Esas tres son exactamente lo que resuelve el backend S3 de la lección 02.

Lectura recomendada

Terraform Language — State, documentación oficial de HashiCorp. Léete la página principal y «Purpose of Terraform State» (unos 10 minutos). Es la explicación de primera mano de por qué el state existe, escrita por quienes decidieron que existiera — y contesta la objeción obvia de «¿por qué no consultar AWS directamente cada vez?».
