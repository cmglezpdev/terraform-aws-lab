Primero, recupera

Sin abrir nada. Las tres son piezas que hoy tocan trabajo, no repaso decorativo.

El rol de tu Lambda tiene dos políticas y la palabra «policy» aparece en ambas. ¿Cuál mira hacia afuera y cuál hacia adentro? La analogía era un uniforme.

La assume_role_policy mira afuera: dice quién puede ponerse el uniforme (lambda.amazonaws.com). La aws_iam_role_policy mira adentro: qué puertas abre el uniforme puesto — hoy, solo escribir en su grupo de logs.

Hoy no tocas la de afuera para nada: quien se pone el uniforme sigue siendo la misma función. Le añades al uniforme una llave más, y verás que es una política nueva pegada al mismo rol, no una línea metida en la que ya existe.

¿Por qué dejamos vivir a application/create-link.ts, si tiene seis líneas y lo confesé en la propia lección? Se fijó una fecha y una condición.

Porque hoy iba a recibir el repositorio de DynamoDB como parámetro y a reintentar cuando un código colisione — y si esa razón no aparecía, el trato era borrarla. La cita textual de la lección 06: «se justifica en la lección 07 […] Ese día handler.ts no cambia ni una línea, y el dominio tampoco. Eso es lo que compras».

Hoy comprobamos si eso era verdad o era humo. Spoiler: se comprueba mirando el git diff, no creyéndome a mí.

La pregunta de tres partes para cualquier pieza de infraestructura con permisos. Enúnciala de memoria. Identidad, quién, sobre qué.

(1) ¿Con qué identidad actúa? (2) ¿Quién puede usar esa identidad? (3) ¿Sobre qué actúa, y quién crea esos recursos?

Para tu Lambda hoy: (1) el mismo rol de siempre, (2) el mismo servicio de siempre — y lo único que cambia es (3): antes actuaba sobre un grupo de logs, ahora también sobre una tabla. Un recurso nuevo, una llave nueva, y las dos cosas las crea Terraform. Cuando la respuesta a una pregunta no cambia, su código tampoco. Compruébalo luego en el diff.

La decisión que parece trivial y no lo es: la clave

Una tabla de DynamoDB exige elegir la clave de partición al crearla, y no se puede cambiar después. Tu reflejo de SQL dice: «un id autoincremental, y ya». Y aquí tropieza dos veces:

  • No existe el autoincremento. No hay un contador central que repartir entre las máquinas que forman la tabla — un contador único es justo lo que no escala, y DynamoDB prefiere no ofrecértelo a ofrecértelo lento. El identificador lo traes tú.
  • La clave es la pregunta, no un número de fila. La única consulta barata es «dame el ítem con esta clave». ¿Qué sabrá tu redirección cuando llegue una petición? GET /{code} — sabe el código y nada más. Si la clave fuera otra cosa, leer un enlace exigiría recorrer la tabla entera.

Así que la clave es code. Y aquí una elegancia que ya tenías comprada sin saberlo: tus códigos salen de randomBytes, y una clave uniformemente aleatoria es el mejor caso posible para DynamoDB — el hash reparte los ítems perfectamente entre particiones físicas, sin puntos calientes. La decisión de la lección 05 (bytes aleatorios, no un contador) resulta ser también la decisión correcta de base de datos.

El contraejemplo que cae en entrevista

«Pon la fecha de clave de partición, así listamos por día.» Cada partición física sirve como máximo 1 000 escrituras por segundo — con la fecha de clave, todo el tráfico de hoy cae en la misma partición, y ese es tu techo aunque la tabla tenga mil particiones aburridas. Se llama hot partition, y se evita en el diseño, no en la operación: la clave se elige para la consulta del producto y para repartir. Listar por día es un informe, y los informes se hacen fuera — está en la ficha.

Anatomía de un servicio

Amazon DynamoDB

Qué es

Un mapa clave → ítem repartido entre muchas máquinas: le das la clave y responde en pocos milisegundos, tengas cien filas o cien mil millones. Sin servidores que gestionar y pagando por petición. La contrapartida exacta: iterar es carísimo — recorrer la tabla (Scan) lee y factura cada byte — y las preguntas que la tabla puede responder se deciden al diseñar las claves, no al escribir la consulta.

Los tipos que existen

Dos decisiones independientes: cómo pagas y qué clase de almacenamiento. PAY_PER_REQUEST (on-demand) cobra por petición y escala a cero — tu caso, y el de casi todo el mundo al empezar. PROVISIONED reserva capacidad por hora, la uses o no: solo compensa con tráfico plano, sostenido y medido. La clase STANDARD_INFREQUENT_ACCESS abarata el almacenamiento un 60% y encarece las peticiones un 25%, para tablas grandes que casi nadie lee. Y aparte: réplicas globales activas-activas, y DAX, una caché en memoria que cobra por nodo-hora esté o no en uso.

Cuánto cuesta

On-demand en us-east-1: 0,625 USD por millón de escrituras y 0,125 USD por millón de lecturas. Los primeros 25 GB-mes de almacenamiento, gratis; después, 0,25 USD/GB-mes. Tu acortador: un ítem ronda los 100 bytes, mil enlaces cuestan 0,000625 USD de escritura, y la tabla en reposo cuesta exactamente cero — este proyecto sigue pudiendo quedarse desplegado. Verificado el 2026-08-28 contra la Price List API.

Tipos de datos, unidades RCU/WRU, límites (el ítem de 400 KB, el 1 MB de Scan), cuándo NO usarlo y las trampas de Terraform: ficha completa de DynamoDB.

Manos a la obra

  1. La tabla, en cuatro argumentos

    En main.tf, encima del bloque de IAM:

    main.tfnuevo recurso
    resource "aws_dynamodb_table" "links" {
  name         = local.name              # "url-shortener"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "code"

  # Solo los atributos que son clave. Declarar "url" aquí provoca
  # un plan infinito: attribute no es un esquema, es la lista de claves.
  attribute {
    name = "code"
    type = "S"

}

    Cuatro argumentos y dos de ellos son trampas conocidas:

    billing_mode tiene el default equivocado para ti

    Si lo omites, el provider elige PROVISIONED — capacidad reservada que se factura por hora, la uses o no, y que además te obligaría a declarar read_capacity y write_capacity. El free tier de 25 unidades lo taparía en tu cuenta… hasta la tabla en que deje de taparlo. Escríbelo siempre, aunque sea para decir lo que querías de todos modos: es la diferencia entre «cero en reposo» y «una reserva silenciosa por hora». ¿Te suena? Es x86_64 otra vez: el default del provider no es el default que tu proyecto quiere.

    Y attribute no significa lo que parece

    Viniendo de SQL, esto parece el CREATE TABLE y pide declarar cada columna: code, url, created_at… No lo hagas. DynamoDB no tiene esquema — cada ítem lleva los atributos que quiera — y este bloque solo enumera los atributos que son clave de la tabla o de un índice. El provider lo documenta con nombre y apellidos: un atributo de más aquí produce un plan infinito — cada apply intenta indexarlo, no puede, y el siguiente plan vuelve a proponer el mismo cambio, para siempre. Es de las pocas trampas de Terraform que ni el validate ni el plan te avisan: la descubres cuando el drift no desaparece nunca.

    Fíjate también en lo que no está: hash_key es ForceNew — cambiarla luego destruye la tabla con sus datos dentro, y por eso la sección anterior de esta lección existe. Las claves se piensan una vez.

  2. La llave nueva del uniforme

    Te debo una corrección: al final de la lección 06 te dije que la política del rol crecería «con dos acciones más». Mentira piadosa del que escribe de memoria — son una: dynamodb:PutItem. La segunda (GetItem) es de la función que redirige, que no existe todavía, y regalársela a esta sería exactamente el vicio que la heurística de la ficha prohíbe: agrupa por permisos significa que quien no lee, no tiene la llave de leer.

    Una acción, un ARN, y ni un asterisco. Nota que es una política nueva pegada al mismo rol, no una línea añadida a write-own-logs: cada política cuenta una historia completa —«esta función escribe en su tabla»—, y el día que la redirección exista podrás leer los permisos del sistema como un índice. Y a diferencia del ARN del grupo de logs, aquí no hay sufijo :* que perseguir: actúas sobre la tabla, no sobre hijos suyos.

  3. El puerto y el adaptador

    Ahora el código. La pregunta que ordena este paso: ¿dónde puede aparecer el SDK de AWS? Por la regla de la lección 06 —nada del package.json ni en domain/ ni en sus reglas— el SDK solo puede vivir en un sitio nuevo. Créalo, e instala el cliente:

    terminalapp/
    mkdir src/infrastructure
pnpm add @aws-sdk/client-dynamodb      # dependencies: se ejecuta en producción
    El SDK rompe tu build de ESM, y el error solo se ve en Lambda

    Parte del SDK está publicado como CommonJS con require("node:https") dentro. esbuild, al empaquetar a ESM, convierte esos require en un stub que busca un require real en el ámbito del módulo… y en un .mjs no existe. El resultado es esta bomba de relojería al invocar:

    Error: Dynamic require of "node:https" is not supported
    at ModuleJob.run (node:internal/modules/esm/module_job:439:25)

    Y lo retorcido: en tu portátil puede no reproducirse. Si importas el bundle desde un contexto CommonJS (un node -e, un test runner en CJS), el stub encuentra el require de ese contexto y funciona — el fallo solo aparece cuando el fichero se carga como ESM de verdad, que es exactamente lo que hace el runtime de Lambda. Me pasó a mí preparando esta lección: mi prueba de humo pasaba y el invoke reventaba.

    El arreglo es darle al stub lo que busca — un require real, fabricado con createRequire e inyectado al principio del bundle con --banner. Actualiza el script de build en app/package.json:

    app/package.jsonscript build
    "build": "esbuild src/index.ts --bundle --minify --sourcemap
  --platform=node --target=node24 --format=esm
  --banner:js=\"import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);\"
  --outfile=dist/index.mjs"

    (En el JSON va todo en una línea; aquí está partido para poder leerlo. Son 93 bytes más de bundle.) La alternativa habría sido volver a CommonJS — pero el ESM de la lección 06 tenía sus motivos, y un banner de una línea no es precio suficiente para renunciar a ellos.

    Pero antes del adaptador, el contrato. La capa de aplicación no va a pedir «un cliente de DynamoDB»: va a declarar qué necesita de la persistencia, en su propio idioma — eso es un puerto, y es una interfaz de TypeScript de las de toda la vida:

    app/src/application/link-repository.tsnuevo · el puerto
    import type { ShortCode } from "../domain/short-code.ts";
import type { TargetUrl } from "../domain/target-url.ts";

export interface Link {
  code: ShortCode;
  url: TargetUrl;
}

/** El puerto: qué necesita la aplicación de la persistencia, en su idioma. */
export interface LinkRepository {
  /** Guarda el enlace. Lanza CodeCollisionError si el código ya está cogido. */
  save(link: Link): Promise<void>;
}

/** Parte del contrato del puerto: cada implementación traduce sus errores a este. */
export class CodeCollisionError extends Error {
  readonly code: string;

  constructor(code: string) {
    super(`Short code already taken: ${code}`);
    this.name = "CodeCollisionError";
    this.code = code;
  }
}
    Por qué el error vive junto al puerto, y no en domain/errors.ts

    Aplica la heurística de la lección 06: ¿qué test se rompería? «Colisión de códigos» es un concepto de persistencia — el dominio genera códigos, pero no sabe que se guardan, así que no puede saber que chocan. Y no es del adaptador, porque cualquier implementación (DynamoDB, Postgres, un mapa en memoria) debe lanzar este mismo error para que la aplicación reaccione igual. Es el idioma del contrato → vive con el contrato. Cuando un fichero no sabe a qué capa pertenece, pregúntale a sus tests.

    De paso, Link se muda aquí y su campo url sube de string a TargetUrl: lo que se guarda es una URL ya validada, y ahora el compilador lo exige.

    Y ahora sí, el adaptador — el único fichero del proyecto que sabe que existe DynamoDB:

    app/src/infrastructure/dynamodb-link-repository.tsnuevo · el adaptador
    import {
  ConditionalCheckFailedException,
  DynamoDBClient,
  PutItemCommand,
} from "@aws-sdk/client-dynamodb";
import { CodeCollisionError, type Link, type LinkRepository } from "../application/link-repository.ts";

export class DynamoDbLinkRepository implements LinkRepository {
  private readonly client: DynamoDBClient;
  private readonly tableName: string;

  // Sin parameter properties: Node borra tipos, no genera código.
  constructor(client: DynamoDBClient, tableName: string) {
    this.client = client;
    this.tableName = tableName;
  }

  async save(link: Link): Promise<void> {
    try {
      await this.client.send(new PutItemCommand({
        TableName: this.tableName,
        Item: {
          code:       { S: link.code },
          url:        { S: link.url },
          created_at: { S: new Date().toISOString() },
        },
        // Sin esto, PutItem es un upsert: machacaría en silencio
        // el enlace de quien tuviera este código antes.
        ConditionExpression: "attribute_not_exists(code)",
      }));
    } catch (error) {
      if (error instanceof ConditionalCheckFailedException) {
        throw new CodeCollisionError(link.code);
      }
      throw error;
    }
  }
}

    Tres cosas de este fichero que valen el precio de la lección:

    La trampa central de hoy: PutItem no inserta — reemplaza

    Sin la ConditionExpression, escribir un código que ya existe devuelve 200 y machaca el ítem anterior. El enlace de otro usuario pasa a apuntar a tu URL, sin error, sin log, sin nada. Es el mismo género de fallo silencioso que el ARN de logs sin :* de la lección 05: no revienta, corrompe. attribute_not_exists(code) convierte «comprueba y escribe» en una sola operación atómica en el servidor — no hay hueco entre mirar y escribir donde otro pueda colarse. Comprobarlo tú antes con un GetItem no cierra ese hueco, y además necesitaría una llave que esta función no tiene.

    Ese { S: … } no es ruido: es el tipado de DynamoDB

    La API nativa exige el tipo de cada valor: S string, N number, B binary. Existe un segundo paquete (@aws-sdk/lib-dynamodb) que lo esconde y te deja escribir objetos planos — para dos atributos no compensa arrastrar otra dependencia, y verlo desnudo una vez enseña qué hay debajo. Cuando el proyecto 02 tenga ítems de verdad, lo reevaluamos.

    Y la condición no pide permisos extra: PutItem con o sin condición es la misma acción de IAM. La llave del paso 2 ya vale.

    Y fíjate en lo que el adaptador no hace

    No valida la URL, no genera códigos, no reintenta, no loguea. Traduce: del idioma del contrato (save, CodeCollisionError) al idioma de la herramienta (PutItemCommand, ConditionalCheckFailedException), y nada más. La prueba de Valibot de la lección 06 tiene aquí su gemela: cambiar DynamoDB por Postgres debe tocar solo este fichero.

  4. El día del juicio para application/

    La promesa era: «recibe el repositorio y reintenta ante colisiones, y handler.ts y el dominio no cambian». Aquí está el caso de uso pagando su deuda:

    app/src/application/create-link.tsse gana el sitio
    import { z } from "zod";
import { generateShortCode } from "../domain/short-code.ts";
import { parseTargetUrl, MAX_URL_LENGTH } from "../domain/target-url.ts";
import { CodeCollisionError, type Link, type LinkRepository } from "./link-repository.ts";

/** La forma del payload: contrato de transporte, no regla de negocio. */
const createLinkInput = z.object({
  url: z.string().max(MAX_URL_LENGTH),
});

const MAX_ATTEMPTS = 3;

export async function createLink(payload: unknown, repository: LinkRepository): Promise<Link> {
  const { url } = createLinkInput.parse(payload);
  const target = parseTargetUrl(url);

  let lastCollision: CodeCollisionError | undefined;
  for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
    const link: Link = { code: generateShortCode(), url: target };
    try {
      await repository.save(link);
      return link;
    } catch (error) {
      if (!(error instanceof CodeCollisionError)) throw error;
      lastCollision = error;   // colisión: código nuevo, misma URL, otra vez
    }
  }
  throw lastCollision;
}

    Lee el bucle despacio, porque es la primera lógica de orquestación real del curso: valida una vez, y ante una colisión regenera solo el código — la URL ya validada no se vuelve a tocar. Solo la colisión se reintenta; cualquier otro error (permisos, red) sube sin tocar. Y a la tercera, se rinde y cuenta la verdad. Con 40 bits de aleatoriedad las colisiones son estadísticamente anecdóticas — el bucle no está ahí porque vaya a ejecutarse mucho, está ahí porque alguien tiene que decidir qué pasa cuando ocurra, y esa decisión es exactamente el trabajo de esta capa: ni del dominio (no sabe que se guarda), ni del adaptador (no decide políticas), ni del handler (no sabe qué es una colisión).

    El handler cambia solo en su papel de raíz de composición: es quien enchufa el adaptador real al caso de uso —

    Esto es la lectura que te mandé: Using global state

    El cliente y el repositorio se crean fuera del handler, a nivel de módulo. Es la recomendación literal de la página de buenas prácticas de la lección 06: el código de módulo corre una vez por arranque en frío, y las invocaciones siguientes heredan el cliente con su conexión TLS ya negociada. Dentro del handler, cada invocación pagaría ese apretón de manos. Y process.env aparece aquí y solo aquí: la configuración es cosa de la frontera, las capas de dentro reciben valores, no variables de entorno.

    Los tests son donde el fake demuestra por qué el puerto vale lo que cuesta. Sustituye create-link.test.ts:

    app/src/application/create-link.test.tsreemplaza
    import { describe, it } from "node:test";
import assert from "node:assert/strict";
import { z } from "zod";
import { createLink } from "./create-link.ts";
import { CodeCollisionError, type Link, type LinkRepository } from "./link-repository.ts";
import { InvalidTargetUrlError } from "../domain/errors.ts";

/** Fake en memoria: mismo contrato, cero AWS. `collisions` hace fallar los N primeros saves. */
class FakeLinkRepository implements LinkRepository {
  saved: Link[] = [];
  attempted: Link[] = [];
  private collisions: number;

  constructor(collisions = 0) {
    this.collisions = collisions;
  }

  async save(link: Link): Promise<void> {
    this.attempted.push(link);
    if (this.collisions > 0) {
      this.collisions--;
      throw new CodeCollisionError(link.code);
    }
    this.saved.push(link);
  }
}

describe("createLink", () => {
  it("saves the link and returns a 7 characters code", async () => {
    const repository = new FakeLinkRepository();
    const link = await createLink({ url: "https://www.google.com" }, repository);
    assert.match(link.code, /^[A-Za-z0-9_-]{7}$/);
    assert.deepEqual(repository.saved, [link]);
  });

  // La forma del payload pertenece al caso de uso, no al dominio.
  for (const bad of [{}, { url: 42 }, { url: null }, null, "not an object"]) {
    it(`rechaza el payload ${JSON.stringify(bad)}`, async () => {
      await assert.rejects(() => createLink(bad, new FakeLinkRepository()), z.ZodError);
    });
  }

  it("propagates the domain error without touching the repository", async () => {
    const repository = new FakeLinkRepository();
    await assert.rejects(() => createLink({ url: "ftp://a.dev" }, repository), InvalidTargetUrlError);
    assert.equal(repository.attempted.length, 0);
  });

  it("retries a collision with a new code and the same url", async () => {
    const repository = new FakeLinkRepository(1);
    const link = await createLink({ url: "https://www.google.com" }, repository);
    assert.equal(repository.attempted.length, 2);
    assert.notEqual(repository.attempted[0]!.code, repository.attempted[1]!.code);
    assert.equal(repository.attempted[0]!.url, repository.attempted[1]!.url);
    assert.deepEqual(repository.saved, [link]);
  });

  it("gives up after three collisions and saves nothing", async () => {
    const repository = new FakeLinkRepository(Infinity);
    await assert.rejects(
      () => createLink({ url: "https://www.google.com" }, repository),
      CodeCollisionError,
    );
    assert.equal(repository.attempted.length, 3);
    assert.equal(repository.saved.length, 0);
  });
});
