AWS Identity and Access Management

El motor que decide, en cada una de las peticiones que tu código hace a la API de AWS, si se permite o se deniega. No es «gestión de usuarios»: es un evaluador de políticas JSON que se ejecuta antes de cada llamada, y cuya respuesta por defecto es no.

Qué es

Cada vez que Terraform, la CLI o la consola hacen algo en AWS, están mandando una petición HTTP firmada a la API de un servicio. Antes de ejecutarla, ese servicio le pregunta a IAM: ¿este principal puede hacer esta acción sobre este recurso, en estas condiciones? IAM reúne todas las políticas aplicables, las evalúa, y devuelve Allow o Deny. Eso es todo lo que hace IAM. Los usuarios, los roles y los grupos son solo las perchas donde cuelgas esas políticas.

Las cuatro palabras que aparecen en toda política y que conviene no confundir nunca:

  • Principal — quién hace la petición. Un usuario IAM, una sesión de rol, un servicio de AWS, el root.
  • Action — qué intenta hacer. Siempre servicio:Operación: s3:PutObject, sns:Publish. Corresponden una a una con las operaciones de la API, no con lo que ves en la consola.
  • Resource — sobre qué. Un ARN.
  • Condition — bajo qué circunstancias. Lo que usaste en la política del topic SNS para que solo tu cuenta pudiera publicar.
La analogía que sí sirve

IAM no es un portero con una lista de invitados en la puerta. Es un juez que vuelve a juzgar cada petición desde cero: no recuerda que te dejó pasar hace un segundo, no tiene contexto, y empieza siempre desde «denegado» salvo que encuentre por escrito un permiso que aplique.

Dónde se rompe la analogía: un juez pondera. IAM no. No hay grados, no hay intención, no hay «casi». Si el ARN del recurso no encaja carácter a carácter con el patrón de tu política, la política no aplica y la respuesta es no. La mayoría de los AccessDenied que vas a ver en tu vida son un ARN mal escrito, no un permiso que falte.

Para qué se usa de verdad

Que una Lambda solo toque su tabla

Tu función del acortador de URLs necesita escribir en links y en ninguna otra tabla. Su rol de ejecución lleva una política con dynamodb:PutItem sobre el ARN exacto de esa tabla. Si mañana alguien mete un bug que borra otra tabla, la petición se deniega antes de llegar a DynamoDB.

Desplegar desde GitHub Actions sin claves

El caso que más impresiona en una entrevista. Un proveedor OIDC y un rol con una política de confianza que dice «acepto tokens de GitHub, pero solo del repositorio x/y y solo de la rama main». Cero secretos guardados en GitHub. Es el proyecto 07.

Que un servicio de AWS actúe sobre otro

Ya lo hiciste: para que Budgets pudiera publicar en tu topic SNS hubo que darle permiso al servicio, no a una persona. Ese permiso vive en el recurso —una política de recurso— y no en ninguna identidad.

Acotar lo que puede hacer Terraform

Un terraform apply con credenciales de administrador puede borrar la producción entera. Con una identidad acotada, el radio de explosión de un error tuyo o de un módulo de la registry que no has leído queda limitado por escrito.

Dejar de usar root

El root de una cuenta no se puede acotar: ignora las políticas de identidad y los SCP por diseño. La única forma de tener límites es dejar de usarlo y trabajar con otra identidad. Es la razón de existir de la lección 04.

Los tipos que existen

Identidades: quién puede hacer una petición

IdentidadQué la distingueCredencialesCuándo
Root Nace con la cuenta. Acceso total e inacotable: las políticas de identidad no le aplican. Correo + contraseña. Puede tener claves de acceso — no las crees. Solo para la docena de tareas que nadie más puede hacer.
Usuario IAM Identidad permanente dentro de una cuenta. Puede tener contraseña de consola, claves de acceso, o ambas. Largo plazo: la contraseña y las claves no caducan solas. Cuenta suelta sin Organizations, o herramientas que no soportan federación.
Grupo IAM No es una identidad. Es un contenedor de usuarios para colgar políticas una vez. Nadie «es» un grupo ni puede autenticarse como tal. Ninguna. Cuando tienes más de dos usuarios con el mismo perfil de permisos.
Rol IAM Identidad sin credenciales propias que otros asumen. Lleva una política de confianza que dice quién puede asumirlo. Temporales, emitidas por STS. Máximo 12 h. Por defecto. Lambda, EC2, ECS, GitHub Actions, otra cuenta, un humano federado.
Usuario de Identity Center Identidad de la organización, no de una cuenta. Se le asignan «permission sets» que se materializan como roles en cada cuenta. Temporales, vía SSO. La recomendación oficial de AWS para humanos en cuanto tienes más de una cuenta.
El criterio de decisión

Rol siempre que puedas; usuario solo cuando no haya forma de entregar credenciales temporales. La primera de las prácticas recomendadas de AWS es literalmente «Require human users to use federation with an identity provider to access AWS using temporary credentials», y la segunda, «Require workloads to use temporary credentials with IAM roles» (Security best practices in IAM).

AWS admite explícitamente cuatro excepciones donde un usuario IAM con credenciales de largo plazo sigue siendo la respuesta correcta: cargas que no pueden usar roles (plugins de WordPress es su ejemplo), clientes de terceros que no soportan Identity Center, acceso a CodeCommit y acceso a Amazon Keyspaces.

Políticas: dónde se escriben los permisos

TipoSe pega aEfectoDónde lo has visto
De identidad, gestionada por AWS Usuario, grupo o rol Concede. La escribe y la actualiza AWS; tú no puedes editarla. SignInLocalDevelopmentAccess, AdministratorAccess
De identidad, gestionada por ti Usuario, grupo o rol Concede. Objeto con ARN propio, reutilizable, versionado (5 versiones). aws_iam_policy — la que escribes en la lección 04
De identidad, inline Una sola identidad Concede. Nace y muere con esa identidad. No se puede reutilizar. aws_iam_user_policy, aws_iam_role_policy
De recurso El recurso: un topic, un bucket, una cola Concede, y es la única que puede nombrar un principal de otra cuenta. aws_sns_topic_policy — lección 02
Política de confianza Un rol Es la política de recurso de un rol: dice quién puede asumirlo. Sin ella el rol es inútil. assume_role_policy
Permissions boundary Usuario o rol No concede nada. Es un techo: el permiso efectivo es la intersección con las políticas de identidad. Cuando delegas la creación de roles a alguien
SCP / RCP Una OU o una cuenta, en Organizations Tampoco conceden nada: son techos para toda la cuenta. El SCP limita principals; el RCP limita recursos. No aplica en tu cuenta suelta
Session policy Una sesión concreta, al asumir el rol Techo temporal para esa sesión. Poco frecuente a mano
Conceder y limitar no son lo mismo

De los ocho tipos de arriba, solo cuatro conceden permisos: las tres de identidad y la de recurso. Los boundaries, los SCP, los RCP y las session policies solo restan. Un permissions boundary con Action: "*" no le da poder a nadie: le quita el techo, nada más. Es el error conceptual que más veces se ve en entrevistas.

Dónde se buscan las acciones

Cada acción que puedes escribir en el elemento Action de una política está documentada en un único sitio: la Service Authorization Reference — Actions, resources, and condition keys for AWS services. Una página por servicio con la lista completa de sus acciones, sus recursos y sus condition keys. La URL sigue el patrón list_<prefijo>.html, con el mismo prefijo que usas en las políticas: list_dynamodb, list_lambda, list_s3. Guarda el índice: es la página de AWS que más vas a reconsultar escribiendo least privilege.

En la tabla Actions de cada página, las tres columnas que importan:

  • Access level — clasifica cada acción en uno de los cinco niveles de la tabla de abajo. Es el criterio objetivo: no adivines el nivel por el prefijo del nombre (Get*, List*, Describe* siguen a la API de cada servicio, no a esta clasificación); mira la columna.
  • Resource types — si trae un tipo de recurso, la acción admite un ARN en Resource; el asterisco marca los obligatorios. Si la columna está vacía, la acción no admite permisos a nivel de recurso — ver la trampa.
  • Condition keys — las claves que puedes usar en Condition con esa acción. No incluye las globales (aws:SourceAccount y compañía), que van aparte.

Los cinco access levels

NivelQué permiteEjemplos
List Enumerar recursos para saber si existen. Literal de la doc: «can list objects but cannot see the contents of a resource». s3:ListBucket
Read Leer el contenido y los atributos de un recurso, sin poder editarlos. s3:GetObject, s3:GetBucketLocation
Write Crear, borrar o modificar recursos. s3:CreateBucket, s3:PutObject, s3:DeleteBucket
Tagging Solo cambiar tags. Una acción que además hace otra cosa (como iam:CreateRole, que puede etiquetar al crear) cuenta como Write. iam:TagRole, iam:UntagRole
Permissions management Conceder o quitar acceso: el nivel a vigilar. AWS recomienda restringir y monitorizar toda política que lo incluya. s3:PutBucketPolicy, casi todo iam:*
El método para least privilege

Decide primero el nivel máximo que quieres conceder («este rol solo List y Read») y filtra la tabla Actions por la columna Access level, en vez de ir adivinando nombres de acciones de memoria. La consola usa exactamente esta clasificación en los policy summaries para resumirte qué concede una política — si ahí aparece un nivel que no querías dar, la política dice más de lo que crees.

Resource types vacío no es opcional

Si la columna Resource types está vacía, esa acción exige "Resource": "*". Ponerle un ARN «para acotar» no acota: la doc dice literalmente «If you specify a resource that is not valid for the action, any request to use that action fails, and the statement's Effect does not apply» — la sentencia entera deja de aplicar y lo que ves es un AccessDenied sin ninguna pista de por qué. Por eso las políticas bien escritas separan sentencias: una con ARN para las acciones que lo admiten, y otra con Resource: "*" para las que no.

Fuentes: Service Authorization Reference y Access levels in policy summaries, leídas el 2026-08-30.

Cómo funciona por dentro

El orden de evaluación

Para cada petición, y en este orden (policy evaluation logic):

  1. Denegación por defecto. Toda petición empieza denegada. La única excepción del sistema entero es el root, que tiene acceso total.
  2. ¿Hay algún Deny explícito? Se miran todas las políticas a la vez —SCP, RCP, de recurso, de identidad, boundaries, de sesión—. Si aparece uno solo que aplique, la respuesta es Deny y se acabó. No hay nada que lo contrarreste.
  3. RCP y SCP de Organizations. Si existen y no permiten la acción, Deny.
  4. Política de recurso. Si concede permiso directamente al ARN de un usuario IAM, ya vale: gana incluso frente a una denegación implícita en la política de identidad. Los roles no funcionan así.
  5. Políticas de identidad. Si ninguna permite la acción, Deny implícito.
  6. Permissions boundary y session policy, si las hay.

De ahí salen las tres reglas que hay que saber decir de memoria:

  • Un Deny explícito gana siempre. Sobre cualquier Allow, de cualquier tipo, de cualquier sitio.
  • Identidad + recurso se suman. Dentro de la misma cuenta basta con que una de las dos conceda el permiso.
  • Identidad + boundary se intersecan. Hacen falta las dos.

El ARN del bucket no es el ARN del objeto

La confusión que más AccessDenied produce en la práctica, y la que te va a morder hoy mismo:

dos ARN distintosS3
# Acciones a nivel de BUCKET: ListBucket, GetBucketVersioning,
# PutBucketPolicy, GetEncryptionConfiguration…
arn:aws:s3:::mi-bucket

# Acciones a nivel de OBJETO: GetObject, PutObject, DeleteObject…
arn:aws:s3:::mi-bucket/*

Son dos espacios de nombres que no se solapan. s3:* sobre arn:aws:s3:::mi-bucket te deja hacer absolutamente todo con el bucket y nada con lo que hay dentro. Y al revés: s3:ListBucket sobre arn:aws:s3:::mi-bucket/* no funciona nunca, porque ListBucket es una operación del bucket. Cuando una política de S3 «no hace nada», mira la barra.

IAM es eventualmente consistente

La trampa que te va a costar un apply

La propia documentación lo dice sin rodeos: «IAM, like many other AWS services, is eventually consistent… We recommend that you do not include such IAM changes in the critical, high-availability code paths of your application» (What is IAM).

En Terraform esto se manifiesta así: creas un rol y, en el mismo apply, un recurso que lo usa. La API que lo consume todavía no ve el rol y responde InvalidParameterValueException: The role defined for the function cannot be assumed o un AccessDenied sin sentido. Vuelves a lanzar el mismo apply sin tocar nada y funciona. Si alguna vez te pasa eso, no estás loco: es esto. El provider de AWS ya reintenta en muchos casos, pero no en todos.

Global, pero con dirección postal

IAM no es regional: un usuario existe en toda la cuenta. Pero el endpoint es único, iam.amazonaws.com, y vive físicamente en us-east-1. Consecuencias prácticas: los recursos IAM no llevan región en su ARN (arn:aws:iam::999999999999:user/terraform, fíjate en el hueco vacío), y una caída de us-east-1 te impide modificar IAM aunque tu infraestructura esté en Irlanda.

Lo que sorprende en la factura

De IAM, nada: es el único servicio de este curso que no puede aparecer en tu factura jamás. Lo que sí aparece es lo que tus permisos dejaron crear. Un iam:* de más no es solo un agujero de seguridad: es la vía por la que un script con un bug, o unas credenciales filtradas, levantan cien instancias GPU en una región que no miras nunca.

Por eso la lección 01 puso el presupuesto antes que nada. IAM limita el radio de explosión; Budgets te avisa de que ha explotado.

Las tareas que solo puede hacer root

La lista corta que justifica que la cuenta root siga existiendo. Todo lo demás se hace con otra identidad (Tasks that require root user credentials):

  • Cambiar el correo, la contraseña o las claves de acceso del propio root.
  • Cerrar la cuenta.
  • Restaurar los permisos de un administrador IAM que se ha bloqueado a sí mismo. Esta es la que importa hoy.
  • Activar el acceso de IAM a la consola de Facturación.
  • Editar o borrar una política de bucket S3 o de cola SQS que deniega a todos los principals — el clásico «me he cerrado la puerta desde dentro».
  • Configurar el borrado con MFA en un bucket de S3.
  • Registrarse en GovCloud, vender instancias reservadas, vincular una cuenta de Mechanical Turk, y ver ciertas facturas con IVA.
Qué hacer con root en cuanto tengas otra identidad

MFA activado (AWS recomienda passkey o llave de seguridad, no una app), cero claves de acceso —si existen, bórralas—, y la contraseña en un gestor. No lo borres: el día que te bloquees a ti mismo con una política, root es tu única salida.

Cuándo NO usarlo

IAM no se elige: está siempre. La decisión real es qué tipo de identidad usar.

Un usuario IAM tiene sentido si

  • Es una cuenta suelta, sin AWS Organizations, y eres la única persona.
  • La herramienta no soporta Identity Center — AWS lo reconoce como caso válido.
  • Necesitas credenciales específicas de CodeCommit o de Amazon Keyspaces.
  • Puedes darle acceso sin claves de largo plazo, con aws login.

No lo uses si

  • La carga se ejecuta dentro de AWS — Lambda, EC2, ECS: eso es un rol.
  • Es CI/CD — GitHub Actions con OIDC y un rol, nunca una clave en un secreto.
  • Hay más de una cuenta o más de una persona — Identity Center.
  • Vas a acabar guardando un AKIA… en un fichero. Ahí ya te has equivocado.
Se confunde conDiferencia realElige el otro cuando
Usuario vs rol El usuario tiene credenciales permanentes. El rol no tiene ninguna: te las presta STS durante 12 h como mucho, y hace falta una política de confianza para pedirlas. Rol, salvo que no haya forma de entregar credenciales temporales.
IAM vs IAM Identity Center IAM gobierna una cuenta. Identity Center gestiona personas a través de muchas cuentas y siempre entrega credenciales temporales. Identity Center en cuanto haya más de una cuenta o más de una persona.
Grupo vs rol Un grupo es una etiqueta para agrupar usuarios; nadie se autentica como grupo. Un rol es una identidad que se asume. Grupo para organizar permisos de humanos; rol para todo lo demás.
Política de identidad vs de recurso La de identidad dice «este principal puede…». La de recurso dice «sobre mí pueden actuar…» y es la única que admite un principal de otra cuenta. De recurso cuando quien actúa es un servicio de AWS u otra cuenta.
Política vs SCP La política concede. El SCP solo pone un techo a toda la cuenta: no concede nada por sí mismo. SCP para poner barreras que ni un administrador de la cuenta pueda saltarse.

En Terraform

La forma correcta de escribir una política es siempre aws_iam_policy_document, nunca un heredoc de JSON: valida la sintaxis en plan, interpola ARN sin errores de comillas, y se lee como HCL.

política gestionada + rolhcl
# 1. El documento: se evalúa en plan, no en apply.
data "aws_iam_policy_document" "lambda_links" {
  statement {
    sid       = "WriteOwnTable"
    actions   = ["dynamodb:PutItem", "dynamodb:GetItem"]
    resources = [aws_dynamodb_table.links.arn]
  }
}

# 2. La política como objeto con ARN propio: reutilizable.
resource "aws_iam_policy" "lambda_links" {
  name   = "lambda-links-write"
  policy = data.aws_iam_policy_document.lambda_links.json
}

# 3. El rol. La política de confianza es OBLIGATORIA:
#    sin ella nadie puede asumirlo y el rol no sirve para nada.
data "aws_iam_policy_document" "assume_lambda" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["lambda.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "lambda" {
  name               = "links-fn"
  assume_role_policy = data.aws_iam_policy_document.assume_lambda.json
}

# 4. Y el pegamento.
resource "aws_iam_role_policy_attachment" "lambda_links" {
  role       = aws_iam_role.lambda.name
  policy_arn = aws_iam_policy.lambda_links.arn
}
Cuatro trampas conocidas

1. aws_iam_policy_attachment es una bomba. Pese al nombre genérico, es exclusiva: se apropia de la política y desasocia a cualquier identidad que no esté listada en ese bloque. Usa siempre las variantes con sujeto — aws_iam_role_policy_attachment, aws_iam_user_policy_attachment, aws_iam_group_policy_attachment. La documentación del provider lo avisa; casi nadie lo lee.

2. Eventual consistency. Un apply que falla con AccessDenied justo después de crear un rol y que funciona al repetirlo no es un fantasma. Ver arriba.

3. force_destroy en aws_iam_user. Sin él, el destroy falla si el usuario tiene claves de acceso, contraseña de consola o dispositivos MFA que no creó Terraform. Y ojo: ponerlo requiere un apply con éxito antes de que el destroy lo tenga en cuenta.

4. Las contraseñas y las claves acaban en el state. aws_iam_user_login_profile expone el atributo password en claro cuando no le pasas una clave PGP, y aws_iam_access_key expone secret. Los dos se escriben tal cual en el fichero de state — el mismo problema que viste en la lección 03, ahora con algo peor que un correo dentro.
