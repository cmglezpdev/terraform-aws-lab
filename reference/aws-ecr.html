Amazon ECR

El registry de imágenes de contenedor de AWS: el sitio donde vive el artefacto que ECS se descarga para arrancar un task. Un Docker Hub privado, dentro de tu cuenta, con permisos de IAM en vez de usuario y contraseña.

Qué es

Un registry de imágenes OCI gestionado. Haces docker push contra él y docker pull desde él, exactamente como con Docker Hub — pero el control de acceso no son credenciales de un servicio de terceros: son políticas de IAM, las mismas que ya usas para todo lo demás.

Lo que resuelve, dicho sin marketing: un contenedor no se despliega, se descarga. Fargate no tiene tu portátil ni tu Dockerfile; necesita una URL desde la que bajarse el artefacto ya construido, en la misma región (para que sea rápido y gratis) y con una autorización que puedas conceder a un rol en vez de a una persona.

La analogía que sí sirve

Es el S3 de las imágenes de contenedor: un almacén de blobs direccionables. De hecho, por debajo, las capas de tus imágenes viven literalmente en buckets de S3 de AWS — por eso, para hacer un pull desde una subred privada sin NAT, no basta con los endpoints de ECR: también hace falta el de S3.

Dónde se rompe la analogía: S3 te da objetos independientes; ECR te da un grafo. Una imagen es un manifiesto que apunta a capas compartidas entre imágenes. Por eso «borrar la imagen vieja» casi nunca libera lo que crees: si la nueva comparte ocho de sus diez capas, borrar la vieja libera dos.

Para qué se usa de verdad

Guardar el artefacto que despliegas

Tu caso: la CI construye la imagen, la etiqueta con el SHA del commit, la sube a ECR, y la task definition de ECS apunta a esa etiqueta. El registry es la frontera entre «construir» y «desplegar».

Dar permiso de pull a un rol, no a una persona

El execution role de ECS hace el pull con credenciales temporales. No hay contraseña que rotar, ni un secreto de registry compartido en cuatro pipelines.

Esquivar los rate limits de Docker Hub

El pull-through cache pone ECR delante de Docker Hub: la primera descarga va al upstream, las siguientes salen de tu registry. Ni límites, ni caídas de un tercero en mitad de un despliegue.

Escanear lo que vas a ejecutar

Cada push dispara un análisis de vulnerabilidades sobre los paquetes de la imagen. Enterarte de un CVE antes de arrancar el task, no en la auditoría de dentro de seis meses.

Replicar la imagen donde la vas a necesitar

Una regla de replicación copia cada push a otras regiones o cuentas. El cluster de Fráncfort hace pull en local en vez de cruzar el Atlántico por cada task que arranca.

El criterio de decisión

Si dudas, privado. «Público» aquí no significa «cómodo de usar»: significa que cualquier persona del planeta puede descargar tu imagen y leer su contenido — incluidas las credenciales que te dejaste en una capa intermedia y creíste borrar en la siguiente.

Cómo funciona por dentro

Autenticación: un token de 12 horas

ECR habla el protocolo estándar del registry de Docker, así que el cliente necesita usuario y contraseña. Lo que hace la CLI es convertir tus credenciales de IAM en una contraseña temporal:

shellel login canónico
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin \
      111122223333.dkr.ecr.us-east-1.amazonaws.com
  • El usuario es literalmente AWS; la contraseña es el token que devuelve GetAuthorizationToken, y vale 12 horas.
  • El token hereda los permisos del principal que lo pidió. No es una llave maestra: si tu rol solo puede leer un repositorio, el token solo puede leer ese repositorio.
  • Para no repetir el login, existe el Amazon ECR Docker Credential Helper: lo configuras una vez en ~/.docker/config.json y Docker pide el token solo cuando lo necesita. Aviso: no soporta MFA.
  • Y en ECS nada de esto ocurre. El pull lo hace el agente con el execution role: no hay docker login, no hay token que guardar, no hay secreto en la task definition. Es la misma distinción de siempre — el pull pasa antes de que tu código exista, así que el permiso es del execution role, nunca del task role.

Tags mutables: el fallo de diseño que heredas de Docker

Por defecto un repositorio de ECR es MUTABLE: puedes volver a subir mi-app:v2 con un contenido distinto y la etiqueta ahora apunta a otra imagen. Eso significa que «desplegar v2» deja de ser una afirmación reproducible: la v2 de hoy no es la v2 de ayer, tu rollback te devuelve a un artefacto que ya no existe, y dos tasks del mismo service pueden acabar corriendo binarios distintos si uno arrancó antes del re-push.

Con IMMUTABLE, el segundo push de la misma etiqueta falla. Es un fallo que quieres: te obliga a etiquetar por SHA de commit o por versión, y a partir de ahí la etiqueta identifica un artefacto, para siempre.

Desde el 23 de julio de 2025 hay cuatro valores, no dos — porque el todo-o-nada dejaba fuera el caso razonable de querer un latest móvil:

ValorQué hace
MUTABLECualquier etiqueta se puede sobrescribir. El valor por defecto.
IMMUTABLENinguna etiqueta se puede sobrescribir. Lo que quieres para las versiones.
IMMUTABLE_WITH_EXCLUSIONInmutable salvo las etiquetas que casen los filtros (p. ej. latest*, dev-*). La opción sensata.
MUTABLE_WITH_EXCLUSIONMutable salvo las que casen. Para proteger unas pocas etiquetas concretas.

Los filtros van en image_tag_mutability_exclusion_filter: de 1 a 5, con filter_type = "WILDCARD" y hasta dos * por patrón.

Lifecycle policies: el coste que crece en silencio

Cada build de tu CI sube una imagen. Ninguna se borra sola. A los seis meses tienes seiscientas revisiones de una aplicación que ejecuta una, pagando 0,10 USD por cada GB-mes de todas ellas. Es el coste oculto de ECR y no avisa: no hay alarma, no hay límite, solo una línea de factura que sube despacio.

La lifecycle policy es la respuesta: un JSON de reglas que ECR evalúa y aplica en las 24 horas siguientes a que una imagen cumpla el criterio.

CampoValores
tagStatustagged · untagged · any (la regla con any debe llevar la rulePriority más alta: se evalúa la última)
countTypeimageCountMoreThan · sinceImagePushed · sinceImagePulled · sinceImageTransitioned
action.typeexpire (borra) · transition (mueve a la clase archive)

Las dos reglas que debería tener todo repositorio, en este orden:

  1. Borrar las untagged a los pocos días. Son las que quedan huérfanas cada vez que re-etiquetas: no las referencia nada y nadie las va a echar de menos.
  2. Quedarse con las N últimas etiquetadas. imageCountMoreThan: 20 te deja margen de sobra para volver atrás y corta la cola infinita.

expire borra la imagen, y eso no se deshace. Antes de aplicar una política nueva, usa la vista previa de la consola o de la API para ver exactamente qué desaparecería.

Aviso, porque internet cuenta lo viejo: durante años el escaneo básico de ECR se describía como «usa Clair». Ya no: hoy es tecnología propia de AWS. Y otro detalle que muerde: al activar el enhanced scanning, solo entran las imágenes subidas en los últimos 14 días; las más antiguas se quedan con estado SCAN_ELIGIBILITY_EXPIRED hasta que las vuelvas a subir.

La diferencia práctica: el básico responde «¿tiene esta imagen una vulnerabilidad conocida hoy?»; el mejorado responde «avísame cuando la tenga». Si el runtime de tu contenedor son dependencias de npm — y en este curso lo son —, el básico no las mira siquiera.

Pull-through cache: el caso de uso real son los rate limits de Docker Hub

Docker Hub limita las descargas: 100 pulls cada 6 horas por IP si eres anónimo, 200 cada 6 horas con cuenta gratuita (docs.docker.com, vigente a 2026-08-30). Un cluster que escala, una pipeline de CI y una NAT Gateway compartida por todo el equipo — que hace que todos salgáis por la misma IP — consumen esa cuota en un rato. El síntoma es un despliegue que falla con toomanyrequests en el peor momento posible, por una razón que no está en tu cuenta de AWS.

Una regla de pull-through cache convierte tu registry en un espejo bajo demanda: pides <cuenta>.dkr.ecr.<region>.amazonaws.com/docker-hub/library/node:22, ECR crea el repositorio la primera vez, se descarga la imagen del upstream y la sirve; las siguientes salen de tu registry. Revalida contra el upstream como mucho una vez cada 24 h.

Upstream¿Credenciales?
ECR Public, Kubernetes (registry.k8s.io), QuayNo
Docker Hub, GitHub Container Registry, GitLab (SaaS), Azure Container Registry, ChainguardSí — un secreto de Secrets Manager cuyo nombre debe empezar por ecr-pullthroughcache/, en la misma cuenta y región
Otro ECR privado (incluso de otra cuenta)Sí, pero por rol de IAM (custom_role_arn), no por secreto

Tres avisos que ahorran una tarde: las imágenes cacheadas cuestan almacenamiento normal (son repositorios como cualquier otro, así que ponles su lifecycle policy); Lambda no puede tirar de pull-through cache; y la primera descarga necesita salida a internet aunque tengas los VPC endpoints puestos — el endpoint te conecta con ECR, no con Docker Hub.

Replicación

Reglas a nivel de registry (no de repositorio) que copian cada push a otras regiones u otras cuentas. Cuatro cosas que hay que saber antes de configurarla:

  • Solo replica hacia adelante. Lo que ya estaba subido antes de crear la regla no se copia; solo lo que se empuje después.
  • Un solo salto. Lo replicado en el destino no se vuelve a replicar desde allí.
  • El permiso lo pone el destino, no el origen: la cuenta destino necesita una política de registry que conceda al origen ecr:ReplicateImage y ecr:CreateRepository.
  • Las copias se pagan. Cada destino es almacenamiento normal a 0,10 USD por GB-mes, más la transferencia entre regiones. Y las lifecycle policies no se replican: si no pones una en el destino, ahí se acumula todo sin límite.

Hacer pull desde una subred privada: la trampa de la factura

Este es el error caro de ECR, y aparece justo en el proyecto 04. Tus tasks de ECS viven en subredes privadas. Para bajarse la imagen tienen dos caminos:

Por NAT GatewayPor VPC endpoints
Cómo llega a ECRSale a internet y vuelve a entrar por el endpoint públicoSe queda dentro de la red de AWS
Qué pagasLa NAT por hora más cada GB procesado, en cada arranque de cada taskLos dos endpoints de interfaz por hora; el de S3 es gateway y no cuesta nada
Qué pasa al escalarVeinte tasks arrancando = veinte descargas de la imagen pagadas a precio de NATIgual de rápido, sin coste por GB

Los endpoints que hacen falta para un pull completo desde una subred sin salida a internet (Fargate platform version 1.4.0 o superior):

VPC endpointslos cuatro, y ni uno menos
com.amazonaws.<region>.ecr.api    (interfaz)  la API de ECR: autorizacion, manifiestos
com.amazonaws.<region>.ecr.dkr    (interfaz)  el protocolo Docker: push y pull
com.amazonaws.<region>.s3         (GATEWAY)   las CAPAS viven en S3 — gratis, y obligatorio
com.amazonaws.<region>.logs       (interfaz)  solo si usas el driver awslogs

El de S3 es el que todo el mundo olvida, y el síntoma es cruel: el task autentica bien, lee el manifiesto bien, y se queda colgado descargando capas hasta que falla con CannotPullContainerError. Como es un gateway endpoint, no cuesta nada — no hay ninguna razón para no ponerlo. Detalles en la ficha de VPC.

Lo que sorprende en la factura

No es el almacenamiento: es la NAT. Una imagen de 500 MB, un service que escala a 20 tasks cuatro veces al día, sin VPC endpoints: son 40 GB diarios cruzando la NAT Gateway y pagándose por GB procesado. El almacenamiento de esa misma imagen cuesta 0,05 USD al mes. El registry es barato; el camino hasta él, no. Y la línea de factura aparece bajo «NAT Gateway», no bajo «ECR», así que cuesta atribuirla.

El segundo: la acumulación silenciosa. Sin lifecycle policy, cada build de cada rama se queda para siempre. Ninguna imagen individual es cara — la suma de mil, sí. Dos reglas de cinco líneas lo resuelven, y hay que ponerlas el día que creas el repositorio, no el día que miras la factura.

Cuándo NO usarlo

Úsalo si

  • Tu cómputo está en AWS: el pull en la misma región es gratis y rápido.
  • Quieres autorizar con IAM, sin credenciales de registry que rotar.
  • La imagen es privada y quieres que siga siéndolo.
  • Necesitas escaneo continuo integrado con el resto de tu seguridad.

No lo uses si

  • Distribuyes una imagen open source al mundo y ya vives en GitHub: GHCR está pegado a tu repositorio y a tus releases.
  • Tu cómputo está en otra nube: pagarías salida a internet en cada pull.
  • Es un experimento local que nunca sale de tu portátil.
Se confunde conDiferencia realElige el otro cuando
Docker Hub Rate limits reales (100 pulls/6 h anónimo, 200 autenticado gratis), autenticación con usuario y contraseña, y latencia de internet en cada pull. ECR no limita las descargas, autoriza con IAM y sirve dentro de la región. Publicas una imagen para el mundo y quieres el sitio donde el mundo la busca primero.
GitHub Container Registry (GHCR) Vive junto al código y a las GitHub Actions que lo construyen; los permisos son los del repositorio de GitHub, no los de tu cuenta de AWS. El pull desde AWS sale por internet. El artefacto es parte del proyecto open source y quien lo consume también está en GitHub. Para un despliegue en AWS, ECR gana por latencia y por coste de transferencia.
Un bucket de S3 con un .tar Guardar la imagen como fichero funciona, pero pierdes todo lo que hace útil a un registry: capas compartidas, resolución de etiquetas, escaneo, y que ECS sepa hacer pull sola. Nunca para imágenes de contenedor. Para el ZIP de una Lambda, sí — es lo que hacéis en el proyecto 01.

En Terraform

HCLrepositorio + limpieza automática
resource "aws_ecr_repository" "app" {
  name                 = "app"
  image_tag_mutability = "IMMUTABLE_WITH_EXCLUSION"

  image_tag_mutability_exclusion_filter {
    filter      = "latest"     # solo esta etiqueta se puede mover
    filter_type = "WILDCARD"
  }

  image_scanning_configuration {
    scan_on_push = true        # basic scanning, gratis
  }
}

resource "aws_ecr_lifecycle_policy" "app" {
  repository = aws_ecr_repository.app.name

  policy = jsonencode({
    rules = [
      {
        rulePriority = 1
        description  = "Borrar las untagged a los 7 dias"
        selection = {
          tagStatus   = "untagged"
          countType   = "sinceImagePushed"
          countUnit   = "days"
          countNumber = 7
        }
        action = { type = "expire" }
      },
      {
        rulePriority = 2
        description  = "Quedarse con las 20 ultimas etiquetadas"
        selection = {
          tagStatus     = "tagged"
          tagPatternList = ["*"]
          countType     = "imageCountMoreThan"
          countNumber   = 20
        }
        action = { type = "expire" }
      },
    ]
  })
}
Trampas conocidas
  • El destroy falla si el repositorio tiene imágenes. Terraform no borra artefactos por su cuenta. O lo vacías a mano, o pones force_delete = true — y entonces sí, el destroy se lleva las imágenes por delante sin preguntar.
  • Solo cabe un aws_ecr_lifecycle_policy por repositorio. Varias reglas van dentro del mismo JSON, no en varios recursos.
  • Las reglas deben ir ordenadas por rulePriority ascendente en el código. La API de ECR las reordena, y si tú las escribiste desordenadas el recurso sale marcado para recrear en cada plan: diff perpetuo.
  • Terraform crea el repositorio, no sube la imagen. El apply termina y el repositorio está vacío: si el service de ECS ya apunta a una etiqueta que nadie ha subido, los tasks mueren en PENDING. El orden es: repositorio → docker push → service.
  • En una regla tagged, tagPatternList y tagPrefixList son excluyentes: uno u otro, nunca los dos.
  • La inmutabilidad y el pull-through cache se pelean. Un repositorio cacheado necesita poder refrescar etiquetas para seguir al upstream; márcalo MUTABLE.
