El state y el refactor: mover sin destruir

Direcciones, for_each, bloques moved y la receta completa del refactor invisible. Verificado ejecutándolo con Terraform 1.15 el 2026-08-29. Fuente primaria: la guía de refactoring de HashiCorp.

La idea que ordena todo

La dirección es la identidad

aws_lambda_function.fn["create-link"]
└────────┬────────┘ └┬┘ └─────┬─────┘
       tipo       nombre   clave de
                           instancia

El plan empareja por dirección, nunca por «configuración equivalente»: lo que está en el código y no en el state se crea; lo que está en el state y no en el código se destruye. Renombrar un recurso, pasarlo a for_each o meterlo en un módulo cambia su dirección — y sin más información, eso es una demolición con obra nueva.

Qué guarda el state

El registro civil: cada dirección casada con su objeto real (ID, ARN, atributos). Un refactor invisible cambia la mitad «dirección» del registro sin tocar la mitad «objeto».

terraform state list        # todas las direcciones
terraform state show DIR    # una, con sus atributos

Con backend S3 ambos comandos necesitan sesión (aws login).

Las cuatro cosas que un plan puede contar

+ / -crear / destruir
~modificar en sitio
-/+destruir y recrear — el objeto muere
sin símbolo# X has moved to Y — mudanza: a AWS no se le pide nada

En un refactor puro, la línea final es la vara: Plan: 0 to add, 0 to change, 0 to destroy.

for_each

Sintaxis mínima

locals {
  functions = {
    "create-link" = { route_key = "POST /links" }
    "get-link"    = { route_key = "GET /{code}" }
  }
}

resource "aws_lambda_function" "fn" {
  for_each      = local.functions
  function_name = "app-${each.key}"
  # each.value.route_key, etc.
}

# referenciar una instancia concreta:
aws_iam_role.fn[each.key].arn      # dentro de otro for_each
aws_lambda_function.fn["get-link"] # desde fuera

Reglas y trampas

  • Acepta un mapa o un set de strings (lista → toset(), no hay conversión implícita).
  • Las claves deben conocerse antes de tocar nada remoto: locals sí; atributos que AWS devuelve en el apply, no. Tampoco valores sensitive.
  • La clave entra en la dirección → renombrarla es otra mudanza. Elígela como un nombre de columna: para no tocarla.
  • depends_on no admite each: apunta al recurso entero (aws_iam_role_policy.logs, sin clave).
  • Borrar una clave del mapa destruye todos sus recursos. El mapa concentra el poder: se revisa como un rm -rf.

count: el hermano posicional

Identidad por índice ([0], [1]…), no por clave. Borra el primer elemento de la lista y todo se corre un puesto: cascada de modificaciones y una destrucción al final. Regla del curso: count para «N copias idénticas o un on/off» (count = var.enabled ? 1 : 0); for_each para todo lo que tenga nombre propio.

Bloques moved

Sintaxis desde Terraform 1.1

moved {
  from = aws_iam_role.create_link
  to   = aws_iam_role.fn["create-link"]
}

Direcciones sin comillas alrededor; la clave de instancia sí va entre comillas (índices de count: [0], sin ellas). Cubre renombrar, pasar a for_each/count y mover a/entre módulos.

Reglas

  • Solo resources (y módulos). Los data sources no se mudan: se releen.
  • No convierte un resource en data source, ni cambia de tipo de recurso (salvo excepciones del provider).
  • Se pueden encadenar: A→B en un commit, B→C en otro; Terraform sigue la cadena.
  • Un moved ya aplicado es inerte. ¿Borrarlo? Depende de quién más aplica: en un módulo publicado, «removing a moved block is a breaking change» y se conservan para siempre; con un único state y un único operador, se borra tras el apply y el siguiente plan (No changes) lo certifica.

moved vs terraform state mv

moveddeclarativo, viaja en el commit, se revisa en PR, el plan lo ensaya antes de hacerlo, lo ejecuta igual cualquiera que aplique
state mvimperativo, edita el state por fuera, sin ensayo ni revisión. No está deprecado: sigue siendo la herramienta para lo que moved no expresa (p. ej. mover recursos entre states distintos)

Casi todo internet enseña state mv para refactors — es anterior a la 1.1. Mismo patrón que el lock con DynamoDB: lo viejo funciona, pero ya no es la forma.

La receta del refactor invisible

Los seis pasos

  1. terraform state list — anota las direcciones viejas.
  2. Escribe el destino (mapa en locals + recursos con for_each).
  3. Un moved por recurso: from = dirección vieja tal como sale en el state; to = nueva con su clave.
  4. plan y léelo entero: N mudanzas sin símbolo, 0 a añadir, 0 a destruir. Cada ~ restante es una diferencia real que el refactor sacó a la luz — nómbrala o no apliques.
  5. apply, y las pruebas: state list (solo direcciones nuevas), segundo plan (No changes), y el humo de la aplicación.
  6. Borra los moved si nadie más aplica este state; consérvalos si el módulo tiene más usuarios.

Autocorrección

Un moved que falta o está mal escrito no rompe nada: reaparece en el plan como pareja destruir/crear, señalándose solo. El plan es el corrector — por eso el refactor de IaC no se revisa leyendo el código, se revisa leyendo el plan.

El refactor como detector

Fundir gemelos obliga a elegir un valor único por atributo — y cada ~ inesperado del plan es una divergencia que llevaba tiempo ahí (un nombre de fichero, una ARN equivalente-pero-distinta). Un diff normalizado con sed no puede verlas: borra justo los errores que viven en los nombres. El plan compara identidades contra el state refrescado; a ese no hay sed que lo engañe.
