Qué es

Un almacén de objetos. Un objeto son tres cosas: unos bytes, una clave (una cadena de texto que lo identifica dentro del bucket) y unos metadatos. Se escribe entero y se lee entero: no puedes modificar el byte 4.096 de un objeto. Si cambias algo, subes el objeto completo otra vez.

Un bucket es el contenedor. Vive en una región concreta y su nombre debe ser único en todo AWS, no solo en tu cuenta.

La analogía que sí sirve

S3 es un guardarropa, no una estantería. Entregas una bolsa, te dan un número, y con ese número recuperas la bolsa entera. No puedes pedir «sácame solo el calcetín izquierdo y cámbialo».

Dónde se rompe la analogía: las claves llevan barras (logs/2026/08/app.log) y la consola las dibuja como carpetas. No hay carpetas. Es una sola cadena de texto plana. Por eso «renombrar una carpeta» en S3 significa copiar cada objeto a una clave nueva y borrar el viejo — y por eso esa operación es lenta y cuesta dinero cuando hay muchos objetos.

Para qué se usa de verdad

El backend del state de Terraform

Es el uso de este curso. Un fichero JSON de unos kilobytes, versionado, cifrado y con bloqueo. Cuesta cero y es el estándar de la industria. Lección 03.

El origen de un sitio estático

El HTML, JS y CSS compilados de un frontend, servidos al mundo a través de CloudFront. El bucket permanece privado; solo CloudFront puede leerlo. Proyecto 05.

Buzón de entrada de datos

Un cliente sube un CSV, S3 emite un evento a EventBridge, una Lambda lo procesa. El bucket es el disparador, no solo el almacén. Proyecto 02.

Data lake y logs

Terabytes de eventos en Parquet que Athena consulta sin moverlos. Aquí es donde las clases de almacenamiento y las reglas de ciclo de vida dejan de ser teoría.

Copias de seguridad y archivo

Volcados de base de datos que hay que conservar siete años por normativa y que casi nunca se leen. Es el caso de Glacier Deep Archive.

Los tipos que existen

En S3 «tipo» significa dos cosas distintas, y conviene no mezclarlas: el tipo de bucket y la clase de almacenamiento de cada objeto.

El criterio de decisión

Si no sabes cada cuánto se lee un objeto, usa INTELLIGENT_TIERING y deja de pensar. No tiene tarifa de recuperación ni duración mínima, y mueve los objetos solo. Cobra una pequeña tarifa de monitorización por objeto, así que deja de compensar cuando tienes millones de objetos diminutos.

Si sí lo sabes: STANDARD para lo que se lee a diario, STANDARD_IA para lo que se lee al mes, DEEP_ARCHIVE para lo que guardas por obligación legal. Y nunca metas en IA o Glacier objetos que vas a borrar pronto: la duración mínima se cobra igual.

Cómo funciona por dentro

Cinco propiedades. Con estas cinco no cometes los errores clásicos:

  • Consistencia fuerte. Desde diciembre de 2020, un GET posterior a un PUT devuelve siempre la versión nueva, sin ventana de inconsistencia y sin coste extra (fuente). El material anterior a esa fecha —que sigue circulando— te dirá lo contrario.
  • Escrituras condicionales. Puedes enviar un PUT con la cabecera If-None-Match: *, y S3 lo rechaza si la clave ya existe (fuente). Esto convierte a S3 en un mecanismo de exclusión mutua. Es exactamente el motor del use_lockfile de Terraform: el lock no es magia, es un objeto que solo puede crear el primero que llegue.
  • El versionado no sobrescribe: apila. Con versionado activo, cada PUT sobre la misma clave crea una versión nueva —con su VersionId, una cadena opaca de hasta 1.024 bytes que solo S3 puede generar— y conserva la anterior como noncurrent. Un DELETE no borra: coloca un delete marker encima, y un GET normal devuelve 404 mientras esté ahí, aunque todas las versiones sigan existiendo (y pagándose: cada versión es el objeto entero, no un diff). Cualquier versión se recupera pidiéndola por su VersionId; borrar de verdad exige borrar versión a versión. El historial completo se consulta con aws s3api list-object-versions. Un bucket pasa por tres estados — sin versionar (todo objeto tiene VersionId null), Enabled y Suspended — y del primero no se vuelve: una vez activado, solo puede suspenderse (fuente).
  • Cifrado en reposo, siempre. Desde el 5 de enero de 2023 todos los objetos nuevos se cifran con SSE-S3 (AES-256) automáticamente, sin coste y sin posibilidad de desactivarlo (FAQ oficial). Si un tutorial te hace escribir un recurso solo para «activar el cifrado», ese tutorial es anterior a 2023.
  • Privado por defecto. «By default, new buckets, access points, and objects don't allow public access» (Block Public Access). Los buckets filtrados de las noticias no eran públicos por descuido de AWS: alguien desactivó esto a mano. Cómo funciona ese «privado» exactamente es la sección siguiente.

El modelo de acceso: quién entra y quién no

Cuando llega una petición —un GetObject, un PutObject, un ListBucket—, S3 la decide consultando hasta cuatro mecanismos distintos. Los cuatro existen a la vez, y la mitad de los sustos con S3 vienen de conocer solo dos de ellos.

MecanismoDónde viveQué respondeEstado hoy
Política de identidad En el usuario o rol «¿Qué puede hacer este principal?» Vigente. La conoces de la ficha de IAM.
Política de bucket En el bucket «¿Quién puede hacer qué sobre este recurso?» Vigente. Es la política de recurso de S3; anatomía abajo.
ACLs En el bucket y en cada objeto «¿Qué cuentas tienen concesiones sobre esta pieza?» Legado. Desactivadas por defecto en todo bucket nuevo.
Block Public Access En el bucket, la cuenta o la organización No concede nada: anula lo que otros concedan al público. Vigente. Activado por defecto en todo bucket nuevo.
Cómo se combinan

El orden mental para evaluar una petición: 1. ¿Alguna política aplica una denegación explícita? Denegada, sin apelación. 2. ¿Block Public Access bloquea este tipo de acceso? Denegada. 3. ¿Algún allow la cubre? Dentro de tu propia cuenta basta con que lo diga o la política de identidad o la del bucket; entre cuentas distintas tienen que decirlo las dos. 4. Si nadie la permite: denegación implícita, el default de todo en AWS (lógica de evaluación).

ACLs y Object Ownership: el mecanismo heredado

Las ACLs (access control lists) son anteriores a IAM: una lista de concesiones pegada al bucket y a cada objeto, con la rareza de que la cuenta que subía un objeto podía quedarse como su dueña aunque el bucket fuera de otra. Dos décadas de tutoriales con --acl public-read salen de ahí — y buena parte de los buckets filtrados de las noticias, también.

Hoy están desactivadas por defecto: todo bucket nuevo nace con el ajuste de Object Ownership llamado Bucket owner enforced, que apaga las ACLs y hace al dueño del bucket dueño de todos los objetos, los suba quien los suba. El control de acceso queda entonces exclusivamente en manos de políticas. Con ese ajuste, PutBucketAcl y PutObjectAcl fallan, y una subida que incluya cualquier ACL distinta de la equivalente al default (bucket-owner-full-control) falla con 400 AccessControlListNotSupported; leer ACLs sigue funcionando. AWS recomienda no reactivarlas salvo que necesites permisos distintos objeto a objeto (Object Ownership).

Los otros dos ajustes —Bucket owner preferred y Object writer— existen para buckets antiguos que aún dependen de ACLs. Para ti la regla es simple: no tocar nada, el default ya es el correcto. En Terraform existe aws_s3_bucket_ownership_controls, pero en un bucket nuevo solo sirve para dejar la intención por escrito.

Block Public Access: el cortafuegos

Cuatro interruptores independientes que se aplican a un bucket, a la cuenta entera o a la organización — y si difieren, gana la combinación más restrictiva. No conceden ni modifican nada: mientras están activos, anulan. Y ahí está su letra pequeña: como no tocan las políticas ni las ACLs existentes, quitarlos devuelve lo público a público (fuente).

BanderaQué hace exactamente
block_public_acls Rechaza las llamadas que intenten poner una ACL pública nueva (PutBucketAcl, PutObjectAcl, PutObject con ACL pública). Las ya existentes no se tocan.
ignore_public_acls Hace que S3 ignore las ACLs públicas que ya existan sobre el bucket y sus objetos. Siguen escritas, pero dejan de contar en la evaluación.
block_public_policy Rechaza PutBucketPolicy si la política que intentas guardar permite acceso público. La política ya guardada no se toca.
restrict_public_buckets Si la política del bucket es pública, corta el acceso a todo el que no sea la propia cuenta o un service principal de AWS — incluidas otras cuentas concretas a las que la política delegara acceso.

La simetría ayuda a recordarlas: dos hablan de ACLs y dos de políticas, y en cada pareja una bloquea lo nuevo mientras la otra neutraliza lo existente. ¿Y qué significa «público»? Una ACL que concede algo a los grupos AllUsers o AuthenticatedUsers; una política que concede a "Principal": "*" sin clavarlo con una condición de valor fijo (una cuenta, una VPC, un rango de IP concreto). Ojo al verbo: público es conceder a todos. Una política que deniega con "Principal": "*" no es pública — es justo lo contrario.

La política de bucket, por dentro

Es la política de recurso de S3: un documento JSON pegado al bucket — uno solo, de 20 KB como máximo. La gramática es la misma que ya usas en IAM —Version, Statement, Effect, Action, Resource, Condition— con una pieza nueva: Principal. Una política de identidad no la lleva porque va pegada a quien la porta; una política de recurso vive en la cosa y tiene que decir a quién se refiere.

El bucket y sus objetos son recursos distintos

arn:aws:s3:::mi-bucket es el bucket; arn:aws:s3:::mi-bucket/* son sus objetos. Las acciones de bucket (s3:ListBucket, s3:GetBucketPolicy) solo casan con el primero; las de objeto (s3:GetObject, s3:PutObject) solo con el segundo. Una statement sobre el ARN equivocado no da error: simplemente nunca aplica. Es el fallo silencioso más común al escribir políticas de S3, y la razón de que el ejemplo de abajo liste los dos ARNs.

El ejemplo canónico — la política con la que AWS recomienda exigir TLS en cualquier bucket (fuente):

denegar todo tráfico sin TLSjson
{
    "Version": "2012-10-17",
    "Statement": [{
        "Sid": "RestrictToTLSRequestsOnly",
        "Effect": "Deny",
        "Principal": "*",
        "Action": "s3:*",
        "Resource": [
            "arn:aws:s3:::mi-bucket",
            "arn:aws:s3:::mi-bucket/*"
        ],
        "Condition": {
            "Bool": { "aws:SecureTransport": "false" }
        }
    }]
}

Léela pieza a pieza, porque todas cargan peso. Deny + Principal: "*": a todos, incluida tu propia cuenta y tu usuario admin. s3:*: cualquier acción. Los dos ARNs: bucket y objetos, por la trampa de arriba. Y la condición: aws:SecureTransport es una condición global — una clave que AWS rellena en cada petición, aquí true si vino cifrada por HTTPS y false si vino por HTTP a secas —, así que la statement solo se activa para el tráfico sin cifrar. Como una denegación explícita gana a cualquier allow, esta política convive en paz con todos los permisos que ya existan: no quita nada a nadie, salvo la puerta HTTP.

Lo que sorprende en la factura

1. Las versiones antiguas se pagan. Activas el versionado, sobrescribes un fichero de 1 GB cada día, y a los tres meses estás pagando 90 GB por un objeto que crees que ocupa uno. La solución es una regla de ciclo de vida que expire las versiones no actuales. Para el state de Terraform da igual: son kilobytes.

2. Las peticiones, no los bytes. Diez millones de objetos de 1 KB ocupan 10 GB (0,23 USD/mes) pero listarlos y leerlos cuesta bastante más que guardarlos. En S3, muchos objetos pequeños es un patrón caro.

3. La salida a internet. Almacenar es barato; sacar los datos, no. Es la razón de poner CloudFront delante de un bucket público, y de por qué «migrar de nube» es caro. La entrada, en cambio, es gratis: entrar es fácil.

4. Los multipart uploads abortados. Una subida grande que falla deja partes huérfanas que ocupan y se facturan, y no se ven en la consola. Se limpian con una regla de ciclo de vida abort_incomplete_multipart_upload. Es el coste fantasma clásico de S3.

El nombre del bucket es global, y eso duele

«Each bucket name must be unique across all AWS accounts in all the AWS Regions within a partition» (naming rules). logs, backups y data están cogidos desde 2007. Por eso todo el mundo escribe algo-<id-de-cuenta> o le pega un sufijo aleatorio.

Peor: al borrar un bucket, otra cuenta puede quedarse con el nombre y empezar a recibir las peticiones que iban dirigidas al tuyo. AWS recomienda literalmente vaciar el bucket y conservarlo antes que borrarlo.

La salida moderna: el account regional namespace. Si nombras el bucket <prefijo>-<id-cuenta>-<región>-an y pasas bucket_namespace = "account-regional", ese nombre queda reservado a tu cuenta para siempre y nadie más puede reclamarlo. El precio es que el ID de cuenta va escrito en el nombre.

Cuándo NO usarlo

Úsalo si

  • Escribes y lees ficheros enteros.
  • El volumen es imprevisible o enorme.
  • Necesitas durabilidad de once nueves sin gestionar nada.
  • Los datos se leen desde varios sitios a la vez.
  • Quieres que subir un fichero dispare un proceso.

No lo uses si

  • Necesitas modificar trozos de un fichero grande.
  • Necesitas semántica POSIX: rename, bloqueo de ficheros, permisos Unix.
  • Consultas por campos, no por clave.
  • Necesitas latencia por debajo del milisegundo.
  • Son millones de registros diminutos que se leen sueltos.
Se confunde conDiferencia realElige el otro cuando
EBS EBS es un disco de bloques que se monta en una instancia EC2. S3 es una API HTTP a la que llega cualquiera. Necesitas un sistema de ficheros con escrituras parciales: la raíz de un servidor, los datos de una base de datos.
EFS EFS es NFS gestionado: semántica POSIX real y montaje simultáneo desde muchas instancias. Cuesta bastante más por GB. Un software heredado espera un /mnt/algo y no lo vas a reescribir.
DynamoDB DynamoDB indexa y consulta registros pequeños en milisegundos. S3 solo sabe buscar por clave exacta o listar por prefijo. Buscas «todos los pedidos de este usuario en marzo». Eso en S3 es un LIST completo, y es caro y lento.
S3 Express One Zone Diez veces más rápido y una sola AZ, a casi cinco veces el precio por GB (0,11 frente a 0,023). La latencia es tu cuello de botella y puedes reconstruir los datos si cae la AZ.

En Terraform

Desde la versión 4 del provider, aws_s3_bucket solo crea el bucket. Cada característica —versionado, ciclo de vida, cifrado, política— es un recurso aparte que apunta al bucket. Si ves un ejemplo con un bloque versioning { } dentro del recurso, es de antes de 2022.

bucket privado y versionadohcl
resource "aws_s3_bucket" "state" {
  bucket = "tf-state-${data.aws_caller_identity.current.account_id}"

  lifecycle {
    prevent_destroy = true   # nadie borra esto por accidente
  }
}

resource "aws_s3_bucket_versioning" "state" {
  bucket = aws_s3_bucket.state.id
  versioning_configuration {
    status = "Enabled"   # Enabled | Suspended | Disabled
  }
}

resource "aws_s3_bucket_public_access_block" "state" {
  bucket                  = aws_s3_bucket.state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

La política de bucket es también su propio recurso, aws_s3_bucket_policy, y el patrón idiomático no es incrustar JSON con jsonencode() sino componerlo con el data source aws_iam_policy_document — el mismo que ya usaste en IAM, que valida la gramática en el plan. En una política de bucket debe llevar bloque principals. El esqueleto:

política de bucket — el esqueletohcl
data "aws_iam_policy_document" "este" {
  statement {
    sid    = "…"
    effect = "…"          # "Allow" | "Deny"

    principals {
      type        = "…"   # "AWS", "Service"… — type "*" + identifiers ["*"] ⇒ "Principal": "*"
      identifiers = ["…"]
    }

    actions   = ["…"]
    resources = ["…"]    # recuerda: bucket y objetos son ARNs distintos

    condition {
      test     = "…"      # el operador: "StringEquals", "Bool"…
      variable = "…"      # la clave de condición
      values   = ["…"]
    }
  }
}

resource "aws_s3_bucket_policy" "este" {
  bucket = aws_s3_bucket.este.id
  policy = data.aws_iam_policy_document.este.json
}
Trampas conocidas

Un solo aws_s3_bucket_policy por bucket. Cada uno llama a PutBucketPolicy, que reemplaza la política entera sin avisar: dos recursos apuntando al mismo bucket se pisan en silencio, ganando el último en aplicarse (provider).

La política y el public access block pueden chocar. Con block_public_policy activo, S3 rechaza cualquier PutBucketPolicy cuya política permita acceso público. Si un mismo apply crea ambos recursos, Terraform no ve ninguna dependencia entre ellos y el orden queda al azar — ese orden lo fijas tú con depends_on cuando importa. Una política que solo deniega no choca: denegar no es «público».

destroy falla si el bucket tiene objetos. S3 no permite borrar un bucket no vacío. El atajo es force_destroy = true, que borra todos los objetos —incluidas todas las versiones— sin posibilidad de recuperarlos. En un bucket de state, nunca.

prevent_destroy = true bloquea el destroy del stack entero, no solo de ese recurso. Es lo que quieres para el bucket del state, pero significa que ese proyecto ya no se tumba con un comando.

Los cuatro true del public access block son redundantes hoy: los buckets nuevos ya nacen así. Se escriben igual, por dos razones — dejan la intención por escrito para quien lea el repositorio, y hacen que Terraform detecte drift si alguien los desactiva a mano. Sobre lo que Terraform no gestiona, no hay plan que valga.

Borrar el recurso aws_s3_bucket_versioning no desactiva el versionado: lo pone en Suspended, que no es lo mismo. Las versiones antiguas siguen existiendo y siguen facturándose.
