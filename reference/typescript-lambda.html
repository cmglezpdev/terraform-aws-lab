Las tres capas, y la pregunta que las decide

Para saber en qué capa va un fichero, una sola pregunta: ¿esto seguiría siendo cierto si el código se ejecutara en tu portátil?

CapaQué vive ahíProhibido importarCómo se prueba
domain/Reglas del negocio, tipos marcados, errores propiosTodo lo que esté en tu package.json. Solo TypeScript y globales del lenguajeDirecto, sin dobles
application/Casos de uso, y validar la forma de lo que entraSDK de AWS, tipos de eventosCon dobles de los puertos
infrastructure/Implementar puertos con el SDK de AWS—Tests de integración
handler.tsTraducir evento ↔ caso de uso, y solo eso—Con eventos falsos
index.tsUna línea: export { handler } from "./handler.ts"——
La línea del dominio es «¿aparece en mi package.json?»

No es solo el SDK de AWS: ninguna dependencia externa entra en domain/ —ni zod, ni un ORM, ni un cliente HTTP—. Una regla de negocio que depende de una librería caduca cuando esa librería cambia de API, y es la parte del código que más años vive.

Globales del lenguaje sí: URL, Date, Intl, node:crypto. No los instalas, están en cualquier runtime.

El reparto correcto cuando validas:

Dónde viveEjemplo
La regladomain/, como dato puro exportadoALLOWED_PROTOCOLS, MAX_URL_LENGTH
La forma del payloadapplication/, con zodz.object({ url: z.string() })
El mecanismoDonde esté la libreríasafeParse, ZodError

Prueba de que está bien separado: cambiar zod por Valibot no debe tocar domain/. Y en los tests, cada caso cae solo en su fichero — { url: 42 } contra el caso de uso, "javascript:alert(1)" contra el dominio. Cuando un caso no sabe a qué fichero pertenece, la frontera está mal puesta.

La prueba de diagnóstico

Léelo al revés y tienes un detector de errores de diseño: si para probar una función necesitas AWS, es que esa función sabe demasiado sobre AWS. La testabilidad no es una consecuencia agradable de las capas: es su definición operativa. Una capa que no se prueba más fácil que la de abajo no se ha ganado el directorio.

Cuándo NO montar capas

Si una función nunca va a tener entrada/salida ni pasos que orquestar, application/ sobra y crearla es cargo cult. El DDD útil no es una lista de carpetas obligatorias: es poner una frontera donde hay una frontera real. Señal de que sí la hay: entra una base de datos, un servicio externo, o hay reintentos.

Tipos marcados (branded types): el value object sin coste

export type ShortCode = string & { readonly __brand: "ShortCode" };

// O, si el tipo nace de un esquema de zod:
const schema = z.httpUrl().brand<"TargetUrl">();
export type TargetUrl = z.infer<typeof schema>;

En tiempo de ejecución sigue siendo un string —cero bytes en el bundle—, pero TypeScript ya no deja pasar cualquier cadena donde se espera un ShortCode. Útil en cuanto manejas dos string distintos a la vez que no deben confundirse.

Validación en la frontera: parse, don't validate

Un validador devuelve true/false y te deja el dato igual de sospechoso. Un parser devuelve un tipo distinto: la comprobación queda registrada en el sistema de tipos y nadie puede saltársela más abajo.

domain/la regla, sin dependencias
export const ALLOWED_PROTOCOLS = ["http:", "https:"] as const;
export const MAX_URL_LENGTH = 2048;
export type TargetUrl = string & { readonly __brand: "TargetUrl" };

export function parseTargetUrl(raw: string): TargetUrl {   // string, no unknown
  // URL es un global del lenguaje. .href normaliza: añade la barra final.
  ...
  return parsed.href as TargetUrl;
}
application/la forma, con zod
const createLinkInput = z.object({ url: z.string().max(MAX_URL_LENGTH) });

export function createLink(payload: unknown): Link {
  const { url } = createLinkInput.parse(payload);   // ¿tiene la forma pactada?
  return { code: generateShortCode(), url: parseTargetUrl(url) };  // ¿cumple la regla?
}
  • El event del handler se tipa unknown, nunca con una interfaz. El tipo desaparece al compilar y quien invoca es AWS: declararlo tipado no valida nada, solo apaga las preguntas del compilador.
  • Cada capa recibe datos más fuertes que la anterior. El handler recibe unknown, el caso de uso lo convierte en { url: string }, el dominio recibe string y devuelve TargetUrl. Eso es «parse, don't validate» aplicado de verdad: la comprobación queda registrada en el sistema de tipos y nadie puede saltársela más abajo.
  • safeParse en la frontera con el mundo, para traducir el fallo a un error tuyo. parse a secas vale dentro, cuando un ZodError que sube es información útil.
  • Cuidado con lo que la librería deja de hacer. new URL(x).href normaliza; z.httpUrl() a secas no, hace falta normalize: true. Al sustituir código propio por una librería, lo que se rompe no es lo que la librería hace peor, sino lo que tu código hacía sin que lo supieras.

Cuántas librerías caben, de verdad

La pregunta no es «¿cuántas puedo meter?» sino «¿en qué se nota?». Medido el 2026-08-27 con esbuild 0.28.2, --minify --format=esm --target=node24, sobre siete dependencias típicas de una API real (zod, cuatro clientes del SDK de AWS —DynamoDB, DocumentClient, S3, SNS—, @aws-lambda-powertools/logger y date-fns):

TamañoFicheros% del límite
node_modules sin bundlear58 MB10 21823% de los 250 MB
Bundle de esbuild1 076 KB10,4%
El .zip que sube286 KB10,6% de los 50 MB

esbuild reduce 58 MB a 1 MB: 54 veces menos. Esa es la respuesta a «¿y cuando tenga muchas dependencias?» — no pasa nada, porque el bundler elimina lo que no alcanzas desde el entrypoint y colapsa 10 000 ficheros en uno. Una API con siete librerías usa el 0,6% del límite de despliegue.

Los límites, para tenerlos delante: 50 MB el .zip subido por la API, 250 MB descomprimido incluyendo layers, 5 layers por función, 10 GB si empaquetas como imagen de contenedor.

Corolario: en una Lambda cabe una aplicación entera

Express, Fastify, Hono o NestJS completos caben de sobra, y se despliegan así en producción con un adaptador que traduce el evento de API Gateway a una petición HTTP. La restricción de Lambda no es el tamaño del código: es el modelo de ejecución —sin estado entre invocaciones, 15 minutos de tope, arranque en frío— y el hecho de que el proceso muere.

Lo que sí conviene vigilar no es cuántos megas pesa, sino qué se ejecuta durante el Init: todo lo que hay fuera del handler corre en cada arranque en frío. Conectar a una base de datos ahí se paga una vez por entorno; leer un secreto de red, también. Ahí es donde se va el tiempo, no en descomprimir.

Cuántas Lambdas: una por endpoint, o una para todas

Los dos extremos tienen nombre. Función de propósito único (una Lambda por operación) y lambdalith (una Lambda con un router dentro, detrás de una ruta comodín de API Gateway). Es un debate abierto de verdad en la comunidad; lo que sigue son los ejes reales, no una respuesta única.

EjeUna por operaciónLambdalith
Permisos IAMEl mínimo exacto de esa operaciónLa unión de todo lo que hace la API
Radio de explosiónUn despliegue roto rompe un endpointRompe la API entera
Memoria y timeoutPor operaciónEl máximo que necesite la peor
Métricas y alarmasPor operación, gratisHay que instrumentarlas a mano
Arranque en fríoBundle menor, pero cada función se calienta por su cuentaBundle mayor, pero una función caliente sirve todas las rutas
EscaladoCada operación escala solaTodo compite por la misma concurrencia
PortabilidadAtado a LambdaEs una app HTTP normal: se mueve a un contenedor sin tocarla
Coste en TerraformCero con for_eachUn recurso
La heurística: agrupa por permisos, no por «entidad»

El eje que decide casi siempre es el primero, porque es el único que no se puede compensar después. Si dos operaciones necesitan permisos distintos, sepáralas; si necesitan los mismos, agruparlas no te cuesta nada en seguridad.

Aplicado a una API de productos: crearProducto y editarProducto escriben en la misma tabla con las mismas acciones — pueden compartir función. listarProductos solo lee: separarla te da una función que no puede escribir aunque la comprometan. Y marcarComoVendido, si además publica en una cola o manda un correo, necesita permisos que ninguna otra tiene: va aparte.

Fíjate en que el criterio no es cuántos endpoints hay, sino cuántos conjuntos de permisos distintos hay. Suelen ser tres o cuatro, no quince.

Lo que AWS dice, y lo que no dice

AWS recomienda «refactor the code into smaller services» según la aplicación crece, y «identify libraries and packages that can be replaced with services to minimize the deployment size», pero reconoce que «monoliths work well for the simplest serverless applications». No hay una regla oficial de «una por endpoint».

Lo que sí es objetivo es el argumento de IAM: los permisos se conceden por función, así que la granularidad de tus funciones es la granularidad de tu privilegio mínimo. Todo lo demás son intercambios discutibles.

El sourcemap se cuela en el zip y no sirve dentro de Lambda

source_dir comprime el directorio entero, y esbuild deja dos ficheros ahí. Node no aplica sourcemaps salvo que arranques con --enable-source-maps (que en Lambda se pone a mano en NODE_OPTIONS y tiene coste de arranque). La solución vive en Terraform:

data "archive_file" "create_link" {
  type        = "zip"
  source_file = "${path.module}/app/dist/index.mjs"   # no source_dir
  output_path = "${path.module}/build/create_link.zip"
}

Verificado con Terraform 1.15.8: con source_file el zip contiene index.mjs en la raíz (usa el basename), así que handler = "index.handler" sigue valiendo. Con varias funciones, un archive_file por función.

Dónde meter una dependencia

OpciónQué implicaVeredicto
Bundlear con esbuildEl código de la librería entra en index.mjsPor defecto, siempre
Subir node_modulesMiles de ficheros; con pnpm son enlaces simbólicosNo
LayerZip aparte montado en /opt, máx. 5 por funciónSolo para binarios pesados compartidos entre muchas funciones
Confiar en el SDK del runtimeAhorra ~500 KB pero la versión menor la elige AWSNo: AWS recomienda empaquetarlo

Una layer con una dependencia JavaScript pura da lo peor de los dos mundos: tu código y sus dependencias dejan de versionarse juntos, y pierdes el tree shaking porque se sube el paquete completo.

Sobre el tree shaking: zod encadena métodos sobre objetos y esbuild no puede demostrar cuáles no usarás — se lleva la librería entera. zod/mini usa funciones sueltas (z.optional(z.string())) y sí se poda, a cambio de una API distinta con métodos que no existen. Optimizar antes de medir el Init Duration real es perder el tiempo.

Tests sin instalar nada

Node 24 trae ejecutor de tests (node:test) y ejecuta TypeScript borrándole los tipos al vuelo. No hace falta Jest, ni Vitest, ni transpilar los tests.

package.jsonscripts
"typecheck": "tsc --noEmit",
"test": "node --test 'src/**/*.test.ts'",
"test:watch": "node --test --watch 'src/**/*.test.ts'",

Comillas simples: el glob lo expande Node, no la shell. Los .test.ts van al lado del fichero que prueban; tsc los comprueba porque entran en include: ["src"], y esbuild no los mete en el bundle porque solo sigue lo que alcanza desde src/index.ts.

tsconfig.jsonuna línea
"noEmit": true,
"allowImportingTsExtensions": true,

Permite escribir import "./errors.ts" con la extensión real, que es lo que hace que el mismo fichero lo entiendan tsc, esbuild y Node. TypeScript solo lo acepta cuando no emites JavaScript — aquí tsc únicamente comprueba.

Sintaxis de TypeScript que Node se niega a ejecutar

Node no compila: borra los tipos y ejecuta lo que queda. Lo que exija generar código falla con SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]:

ProhibidoEscribe en su lugar
constructor(readonly x: string) (parameter property)Campo declarado y asignado a mano
enum Estado { … }const Estado = {…} as const + tipo derivado
namespace X { … }Un módulo

Mensaje literal del error: «TypeScript parameter property is not supported in strip-only mode». Verificado con Node 24.18.0.

Qué prueba cada nivel, y qué no

NivelPruebaCiego a
pnpm run testReglas, casos límite, traducción del handlerRol, permisos, ARNs, handler mal apuntado, runtime
terraform planQue el artefacto cambió (source_code_hash)Si el código funciona
aws lambda invokeQue el paquete arranca y el rol bastaConcurrencia, casos límite que no invocas
aws logs tailQue logs:PutLogEvents sobre el ARN correcto funciona—

Un test unitario no prueba infraestructura. Pasaría entero con el rol roto y el ARN mal escrito. No los invalida: los separa.

El orden, siempre igual

terminalnunca al revés
cd app
pnpm run typecheck && pnpm run test && pnpm run build
cd ..
terraform plan       # aquí se resuelve archive_file: falla si dist/ no existe
terraform apply

El build no entra en Terraform. Terraform gestiona infraestructura; construir artefactos es trabajo del pipeline. Y el orden no es una preferencia: data "archive_file" se resuelve durante el plan.

Comprueba

  1. ¿En qué capa va «una URL de más de 2048 caracteres no se acorta», y por qué no en el handler?
  2. Tu plan dice «No changes» después de cambiar el código. ¿Qué se te olvidó?
  3. ¿Por qué se tipa el event como unknown y no con una interfaz?
  4. El SDK de AWS ya viene en el runtime. Da el argumento de AWS para empaquetarlo igualmente.
  5. Node revienta con ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX. Nombra las tres sintaxis que lo provocan.
