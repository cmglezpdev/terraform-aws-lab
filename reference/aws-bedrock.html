Amazon Bedrock

Modelos fundacionales —Claude entre ellos— servidos como una API más de AWS: el llamante se autentica con IAM, la factura llega en la de AWS, y no existe ninguna clave que guardar. No es un modelo nuevo ni un producto de AWS: es la puerta, y lo que compras al cruzarla es que la credencial deje de ser un secreto tuyo.

Qué es

Un catálogo de modelos fundacionales de varios proveedores (Anthropic, Amazon Nova, Meta, Mistral, OpenAI, Qwen, xAI…) expuesto detrás del plano de control de AWS. Concretamente Bedrock te da cuatro cosas que no tienes llamando al proveedor directamente:

  • Autenticación por IAM. No hay API key. Tu Lambda firma la petición con su rol de ejecución, igual que cuando escribe en DynamoDB. La regla del curso —cero secretos en el repo— deja de necesitar disciplina: no hay secreto que se pueda colar.
  • Una sola factura. Los tokens aparecen en la factura de AWS, dentro del mismo presupuesto y las mismas alarmas del proyecto 00.
  • Un formato común. La API Converse habla igual con Claude que con Nova: cambias un modelId y no tocas el resto del código.
  • Piezas alrededor: guardrails, RAG gestionado, agentes, logging de invocaciones a S3/CloudWatch, todo con recursos IAM y de red de AWS.

Lo que no es: un modelo propio de AWS, ni un hosting donde tú despliegas pesos, ni algo que se «arranque» y se «pare». En reposo no existe: es un endpoint.

La analogía que sí sirve

Un datáfono. El modelo lo pone otro (Anthropic), la infraestructura y el cobro los pone AWS, y tú solo pasas la tarjeta que ya tenías —tu rol IAM—. Dónde se rompe: el datáfono cobra comisión por operación y aquí la comisión es cero; el precio por token del endpoint global es exactamente el de Anthropic. Lo que pagas de más, si lo pagas, es por exigir dónde se procesa (+10 %), no por pasar por AWS.

Para qué se usa de verdad

Un endpoint propio delante del modelo

Tu caso: el proyecto 03. Una Lambda con Function URL recibe el prompt, llama a Claude con su rol, cachea la respuesta en DynamoDB con TTL y devuelve el stream. Ningún cliente ve nunca una credencial del modelo.

Clasificar y extraer sin montar nada

«De estos 40 000 tickets, dime cuáles son bajas.» Con batch inference se lanza como un job asíncrono y cuesta la mitad. Sin servidores, sin colas propias.

Chat sobre documentos de la empresa

Knowledge Bases indexa un bucket S3 y responde citando la fuente. El RAG completo —chunking, embeddings, reranking— sin escribir el pipeline.

Poner un filtro delante y detrás

Guardrails bloquea temas vetados, PII y prompt injection antes de que el prompt llegue al modelo y después de la respuesta. Es política, no ifs en tu código.

Auditar quién llamó y con qué

Cada invocación deja rastro en CloudTrail, y el model invocation logging puede volcar prompts y respuestas a S3. En un entorno regulado esto es el requisito, no un extra.

El paso previo que sorprende: model access

El primer InvokeModel de una cuenta nueva casi siempre devuelve AccessDeniedException, y el error no dice por qué. Bedrock no vende los modelos de terceros: los revende a través de AWS Marketplace, y hay tres puertas distintas antes de la primera respuesta.

PuertaQué esCuándo la cruzas
Permisos de Marketplace aws-marketplace:Subscribe, Unsubscribe, ViewSubscriptions en el rol que invoca Solo la primera vez que se usa el modelo en la cuenta. Después, invocar no los necesita.
El formulario FTU de Anthropic «First Time Use»: nombre de empresa, web, industria, usuarios previstos y descripción del caso de uso. Solo para modelos de Anthropic. Una vez por cuenta —o por cuenta raíz de la organización, y se hereda—. El acceso se concede inmediatamente al enviarlo: no hay revisión humana esperándote.
El acuerdo por modelo La suscripción de Marketplace a ese modelo concreto (EULA incluido) Bedrock la inicia sola en la primera invocación. Tarda hasta 15 minutos, y durante ese rato las llamadas pueden fallar y luego empezar a funcionar sin que hayas tocado nada.

Detalles que ahorran una tarde: el formulario admite un GitHub o un portfolio personal como «web de empresa» si eres un desarrollador individual; el acceso concedido en una región vale para todas las demás donde el modelo exista; y borrar el acceso no bloquea nada —volver a invocar lo recrea—, así que si quieres prohibir un modelo, se prohíbe con un Deny de IAM o una SCP sobre bedrock:InvokeModel, no quitando la suscripción.

La excepción que casi nadie conoce

El formulario FTU no aplica si llamas por el endpoint bedrock-mantle (ver la tabla de integraciones más abajo). Si te has atascado en el formulario y solo quieres la Messages API, esa puerta ni existe.

Los tipos que existen

«Bedrock» es cuatro decisiones independientes que la gente confunde entre sí: por qué endpoint entras, con qué API hablas, por qué perfil de inferencia se enruta y en qué service tier se factura.

El criterio de decisión

Converse por defecto. La documentación lo dice sin rodeos: «provides a consistent API that works with all Amazon Bedrock models that support messages… you can write code once and use it with different models». Además es donde viven tool use y la integración con Guardrails. Baja a InvokeModel solo cuando puedas nombrar el parámetro concreto que te falta; y si lo que quieres es exactamente la API de Anthropic, no bajes a InvokeModel: sube a bedrock-mantle.

El streaming, de punta a punta. ConverseStream te devuelve un flujo de eventos, pero eso solo sirve si tu propio endpoint también sabe emitir a trozos. Ahí entra la Lambda Function URL con invoke_mode = "RESPONSE_STREAM": sin ella, tu Lambda acumula el stream de Bedrock en memoria y lo entrega de golpe al final —y habrás pagado la latencia sin comprar la sensación de rapidez—. API Gateway no hace streaming: es el motivo real de que el proyecto 03 use una Function URL para la ruta de chat.

3. Los tres enrutados: in-region, geo y global

Un inference profile es un alias sobre un modelo que dice a qué regiones puede irse la petición. Se elige poniendo un prefijo en el modelId:

EnrutadomodelIdDónde se procesaPrecio
Globalglobal.anthropic.claude-opus-5 Cualquier región comercial del mundo El de referencia — «approximately 10% savings»
Geo (US, EU, AU, JP)us.anthropic.claude-opus-5 Dentro de esa geografía (US incluye Canadá)+10 %
In-regionanthropic.claude-opus-5 Solo esa región+10 %, y no está disponible para todos los modelos
Por qué a veces el perfil es obligatorio

Claude Opus 5 sobre bedrock-runtime tiene In-Region marcado como no soportado en todas las regiones, us-east-1 incluida: solo Geo y Global. Es decir, el modelId «a secas» que copiaste de un tutorial de 2024 no funciona y devuelve un error de validación. Regla práctica para el curso: usa siempre el prefijo global. — es el más disponible y el más barato, y solo lo cambias si alguien te exige residencia de datos.

Hay además application inference profiles: copias un perfil del sistema, le pones tags, y a partir de ahí el coste de ese equipo o proyecto sale separado en Cost Explorer. Eso sí es un recurso de Terraform (aws_bedrock_inference_profile); los perfiles del sistema (global., us.) ya existen y no se crean.

Cómo funciona por dentro

El modelo mental mínimo para no cometer errores caros:

  • Es síncrono y sin estado. Cada llamada lleva la conversación entera. No hay «sesión» en Bedrock: si tu chat recuerda algo, es porque tú lo guardaste (DynamoDB, en el proyecto 03) y lo reenviaste. El coste crece con el cuadrado de la conversación si no cacheas.
  • No hay clave. La petición se firma con SigV4 usando las credenciales del rol. En una Lambda eso significa: no hay variable de entorno, no hay Secrets Manager, no hay rotación. Solo un Allow sobre bedrock:InvokeModel*. (Existen Bedrock API keys de portador para desarrollo local; la propia documentación de Anthropic las llama la opción least preferred, y en el curso no se usan.)
  • Se factura por token, en los dos sentidos. Entrada y salida a precios distintos —la salida cuesta 5× la entrada en toda la familia Claude— y todo lo que reenvías se vuelve a cobrar como entrada.
  • Prompt caching no es una caché de respuestas. Cachea el prefijo del prompt (system prompt, herramientas, documentos) para no reprocesarlo. Escribir en la caché cuesta 1,25× la entrada (TTL 5 min) o 2× (TTL 1 h); leer cuesta 0,1×. Sale rentable a partir de la primera lectura con TTL de 5 minutos. En Claude Opus 5: mínimo 512 tokens por checkpoint, máximo 4 checkpoints. No ahorra nada si la respuesta es la misma para la misma pregunta: eso es la caché de DynamoDB, otra cosa distinta.
  • Cross-region no cuesta más ni sale de AWS. «There's no additional routing cost… All data transmitted during cross-Region operations remains on the AWS network and does not traverse the public internet.» El precio se calcula por la región desde la que llamas. CloudTrail registra dónde se procesó en additionalEventData.inferenceRegion.
  • Los límites que te van a frenar son de throughput, no de tamaño. Un ThrottlingException por TPM es la incidencia típica en producción, y no se arregla con reintentos inmediatos: se arregla con backoff, con caché, o pidiendo cuota.

La factura del proyecto 03

Por qué el ROADMAP dice «~0 USD + tokens»

Nada de lo que despliega el proyecto 03 cobra por hora. La Lambda, la Function URL, la tabla DynamoDB on-demand, el REST API con usage plans y el modelo habilitado en Bedrock suman 0,00 USD en reposo: el gateway puede quedarse desplegado meses. Los números concretos, con Claude Sonnet 5 por el endpoint global:

  • Una respuesta típica —2 000 tokens de entrada, 500 de salida— cuesta 2 000 × 2,00/10⁶ + 500 × 10,00/10⁶ = 0,009 USD. Nueve milésimas de dólar.
  • Mil respuestas al mes: 9 USD. Dentro del presupuesto de 30 USD/mes del curso, y sin más líneas en la factura.
  • Con la caché de DynamoDB acertando el 50 %, esas mil respuestas bajan a 4,50 USD — y las lecturas de DynamoDB que las sustituyen cuestan céntimos. Ese es el argumento entero de la caché, en dos números.
  • Con Opus 5 en lugar de Sonnet 5, la misma factura se multiplica por 2,5. Con perfil geo en lugar de global, por 1,1 encima de eso.
Lo que sorprende en la factura
  1. Reserved tier / provisioned throughput. Es la trampa seria. Con Opus 4.6, reservar el bloque más pequeño que publica la tabla —1 000 TPM de entrada y 1 000 de salida— cuesta 0,30 + 1,50 = 1,80 USD/h, es decir 1 314 USD al mes, se use o no se use, durante el mes o los tres meses del compromiso. Y esos 1 000 TPM son ridículos: un solo prompt largo los consume. Para los modelos propios de Amazon, donde AWS sí publica el precio del provisioned throughput clásico, un model unit de Nova Pro son 60,50 USD/h sin compromiso y 55,00 USD/h con uno de un mes — 40 150 USD al mes por unidad. Para los modelos de Anthropic el precio del provisioned throughput ni siquiera es público: «reach out to your account team», que es la forma educada de decir que no es para ti. En este curso no se toca jamás. Se justifica cuando tienes tráfico sostenido y medido durante meses; nunca «por si acaso», y nunca antes de haber visto un ThrottlingException real.
  2. El vector store de un Knowledge Base autogestionado. El KB no cobra por hora: el almacén sí. Una colección clásica de OpenSearch Serverless factura un mínimo de 2 OCU a 0,24 USD/OCU-hora = 0,48 USD/h ≈ 350 USD al mes con cero consultas. Es el clásico «probé RAG un fin de semana» que aparece en la factura de dos meses después. Salidas: la Knowledge Base gestionada (AWS pone el almacén y factura por GB y por llamada, sin suelo horario), las colecciones NextGen de OpenSearch Serverless —que escalan a cero tras 10 minutos de inactividad— o S3 Vectors, pensado justo para cargas de consulta poco frecuente.
  3. El +10 % silencioso. Copiar us.anthropic.… de un tutorial en vez de global.anthropic.… encarece cada token un 10 % sin ningún aviso, sin ningún cambio visible en el comportamiento y sin ninguna línea separada en la factura.
  4. Los tokens de salida son el 80 % del gasto de un chat. Cuestan 5× la entrada. Antes de optimizar prompts, mira max_tokens.

Cuándo NO usarlo

Úsalo si

  • El que llama ya vive en AWS y tiene un rol: la credencial deja de existir como problema.
  • Quieres una sola factura, un solo presupuesto y una sola alarma.
  • Necesitas Guardrails, RAG gestionado o auditoría de prompts en S3.
  • Tienes requisitos de residencia de datos: los perfiles geo los resuelven en un prefijo.
  • Vas a comparar modelos de proveedores distintos con el mismo código (Converse).

No lo uses si

  • Necesitas una función que Anthropic acaba de sacar: en Bedrock llega más tarde.
  • Tu cliente no está en AWS: entonces IAM es fricción, no ventaja.
  • Dependes de structured outputs, Files API, web search o code execution del servidor.
  • Quieres Message Batches, Managed Agents o el fallbacks del servidor.
  • Te frena la burocracia de model access para un prototipo de una tarde.

El veredicto para el proyecto 03

Al mismo precio por token, la pregunta se reduce a una sola: ¿dónde vive el que llama? Si es una Lambda tuya en AWS, Bedrock gana porque elimina el secreto —y un secreto que no existe no se filtra, no se rota y no aparece en un git log—. Si el que llama es una app móvil, un script de tu portátil o un backend en otra nube, IAM se convierte en burocracia y la API directa es más honesta. Y un matiz de 2026 que rompe la falsa dicotomía: existe una tercera opción, Claude Platform on AWS, operada por Anthropic con facturación por AWS Marketplace y paridad de funciones casi el mismo día — factura de AWS y funciones al día, a cambio de no tener Guardrails ni Knowledge Bases.

Tres patrones que vas a reconocer

Gateway con caché y rate limiting

El proyecto 03. REST API con usage plans → API key por cliente y cuota por cliente (eso solo lo tiene REST API). Detrás, una Lambda que primero busca en DynamoDB por el hash del prompt; si acierta, devuelve sin gastar un token; si falla, llama a ConverseStream y guarda con ttl para que el ítem caduque solo. Las dos piezas atacan cosas distintas: la caché baja el coste, el usage plan protege la cuota TPM de que un cliente se la coma entera.

Guardrail delante del chatbot

Un aws_bedrock_guardrail con temas vetados y filtro de PII, referenciado en la llamada a Converse. El prompt se evalúa antes de llegar al modelo y la respuesta antes de salir. A 0,15 USD por 1 000 unidades de texto es más barato que el incidente, y sobre todo es una política versionada en Terraform en vez de una lista de ifs enterrada en el código.

RAG con Knowledge Base

Un bucket S3 como data source, una Knowledge Base gestionada encima y RetrieveAndGenerate desde la Lambda. En Terraform — y dónde se acaba el IaC

Esta es la sección que el proyecto 03 usa para hablar de los límites del IaC, así que conviene la frontera exacta. Bedrock tiene muchos recursos, pero la mitad interesante del servicio no es infraestructura:

Lo que sí es TerraformLo que no lo es
  • El permiso: la policy IAM que deja invocar
  • El acuerdo de acceso a cada modelo
  • El formulario FTU de Anthropic
  • Guardrails y sus versiones
  • Application inference profiles (etiquetado de coste)
  • El logging de invocaciones
  • Knowledge bases, data sources, agents, flows, prompts
  • Provisioned throughput (que no vas a crear)
  • La invocación (Converse, InvokeModel): es código de la Lambda
  • El prompt: es un artefacto de producto, no de infraestructura
  • El modelo elegido: casi siempre una variable de entorno, para poder cambiarlo sin un apply
  • Los perfiles del sistema (global., us.): ya existen, no se crean ni se destruyen
  • Las subidas de cuota: un ticket, no un recurso

La lección general: Terraform gestiona capacidades y permisos, no comportamiento. Un plan te dice quién puede llamar a Claude; jamás te dirá qué le va a pedir.

Los recursos del provider

RecursoPara quéTrampa
aws_bedrock_use_case_for_model_access El formulario FTU de Anthropic, como form_data en JSON Recurso raro: si ya existe, lo «adopta» en vez de crearlo; no se puede actualizar (cualquier cambio es un error); y destroy solo lo saca del state — el borrado real no existe.
aws_bedrock_foundation_model_agreement La suscripción de Marketplace a un modelo concreto El offer_token lo da un data source y cambia: sin ignore_changes tienes diff perpetuo.
aws_bedrock_guardrail + aws_bedrock_guardrail_version La política de filtrado y su versión inmutable El guardrail «vivo» es un borrador: lo que se invoca es una versión. Editar el guardrail no cambia lo que ve producción hasta que publicas.
aws_bedrock_inference_profile Perfil de aplicación con tags, para separar coste por equipo o proyecto Copia un perfil existente con model_source.copy_from. No sirve para crear global. ni us.: esos son SYSTEM_DEFINED.
aws_bedrock_model_invocation_logging_configuration Volcar prompts y respuestas a S3 o CloudWatch Único por región. Dos configuraciones en dos states se machacan mutuamente. Y el bucket necesita su bucket policy para bedrock.amazonaws.com antes (depends_on).
aws_bedrock_provisioned_model_throughput Reservar model units commitment_duration vale OneMonth o SixMonths. Un apply distraído aquí es una factura de cuatro cifras que el destroy no te devuelve. Además, los inference profiles no soportan provisioned throughput.
aws_bedrockagent_knowledge_base, _data_source, _agent, _agent_alias, _flow, _prompt RAG, agentes y orquestación Ojo al subcategory: son «Bedrock Agents», prefijo bedrockagent_ sin guion bajo intermedio.
aws_bedrockagentcore_* (runtime, gateway, memory, browser, code_interpreter, policy…) AgentCore, la plataforma de agentes en producción Familia grande y nueva. No hace falta para nada de este curso.

Lo que de verdad escribes en el proyecto 03

HCLel permiso, que es casi todo
locals {
  # El perfil global: mismo modelo, 10 % más barato que us./eu.
  model_id = "global.anthropic.claude-sonnet-5"
}

data "aws_caller_identity" "current" {}
data "aws_region" "current" {}

data "aws_iam_policy_document" "invoke_claude" {
  # 1) el perfil de inferencia, en tu cuenta y tu región
  statement {
    actions   = ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream",
                 "bedrock:Converse", "bedrock:ConverseStream"]
    resources = [
      "arn:aws:bedrock:${data.aws_region.current.region}:${data.aws_caller_identity.current.account_id}:inference-profile/${local.model_id}"
    ]
  }

  # 2) y ADEMAS el foundation model detras del perfil.
  #    Con un perfil global, el ARN sin region es obligatorio.
  statement {
    actions   = ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream",
                 "bedrock:Converse", "bedrock:ConverseStream"]
    resources = [
      "arn:aws:bedrock:${data.aws_region.current.region}::foundation-model/anthropic.claude-sonnet-5",
      "arn:aws:bedrock:::foundation-model/anthropic.claude-sonnet-5",
    ]
  }
}

resource "aws_lambda_function" "gateway" {
  # ...
  environment {
    variables = {
      # el modelo va en variable de entorno: cambiarlo no es un apply
      BEDROCK_MODEL_ID = local.model_id
      CACHE_TABLE      = aws_dynamodb_table.cache.name
    }
  }
}

resource "aws_lambda_function_url" "gateway" {
  function_name      = aws_lambda_function.gateway.function_name
  authorization_type = "AWS_IAM"
  invoke_mode        = "RESPONSE_STREAM"   # sin esto no hay streaming
}
Trampas conocidas, en orden de dolor
  • Autorizar el perfil no autoriza el modelo. La documentación es explícita: «When you specify an inference profile in the Resource field…, you must also specify the foundation model in each Region associated with it». Con un perfil global., ese ARN es el sin región (arn:aws:bedrock:::foundation-model/…). Faltando uno de los dos: AccessDeniedException, y el mensaje no dice cuál falta.
  • bedrock-mantle es otro service prefix. Si usas el endpoint nuevo, la acción no es bedrock:InvokeModel sino bedrock-mantle:CreateInference. Una policy correcta para uno no sirve para el otro.
  • El modelId de los tutoriales viejos no vale. Los IDs con fecha y versión (anthropic.claude-3-5-sonnet-20241022-v2:0) son de la generación anterior; los actuales son limpios (anthropic.claude-sonnet-5) y casi siempre necesitan prefijo de perfil.
  • Sin invoke_mode = "RESPONSE_STREAM" no hay streaming, por mucho que llames a ConverseStream: la Lambda bufferiza y entrega al final.
  • El AccessDeniedException del primer día casi nunca es la policy. Es model access: el formulario FTU sin enviar, o los 15 minutos de la suscripción automática. Compruébalo con aws bedrock get-foundation-model-availability --model-id … antes de tocar IAM.
  • bedrock:* en la policy es tentador y está mal. Incluye crear provisioned throughput. Ver la ficha de IAM.
