Amazon API Gateway

El recepcionista de tu API: recibe HTTPS de internet, decide qué ruta va a qué backend, rechaza a quien no debe pasar, y cobra por petición. Tu Lambda no tiene puerto ni servidor — sin una puerta delante, nadie puede llamarla desde fuera.

Qué es

Un servicio gestionado que se planta entre internet y tu backend: termina el TLS, lee el método y la ruta de cada petición (POST /links), y la entrega al destino que tenga configurado — una Lambda, otro servicio de AWS o cualquier URL. No ejecuta tu código: enruta, filtra y traduce. Existe porque una Lambda no es un servidor: no escucha en ningún puerto, solo responde a invocaciones — y la única forma legal de invocarla desde fuera de AWS es que un servicio con permiso lo haga por ti.

La analogía que sí sirve

El recepcionista de un edificio de oficinas: tú no entras a la planta 7 — le dices a quién buscas, él comprueba la lista, llama arriba y te hace pasar o no. Las oficinas ni siquiera tienen puerta a la calle. Donde se rompe: un recepcionista cobra sueldo fijo esté el edificio vacío o lleno; una HTTP API cobra por visita — cero visitas, cero coste. Esa diferencia es exactamente la que hay con un ALB, que sí cobra por hora.

Para qué se usa de verdad

Dar URL pública a una Lambda

Tu caso: el acortador tiene cerebro y memoria, pero nadie de fuera puede llamarlo. La puerta convierte POST /links en una invocación con permiso.

Autenticación sin escribirla

Un authorizer JWT valida los tokens de Cognito o de cualquier OIDC antes de que tu función se ejecute (y pague). El 401 lo pone la puerta, no tu código.

Proteger el backend del pico

Throttling: si alguien te hace 50 000 peticiones por segundo, la puerta devuelve 429 y tu base de datos ni se entera. Configurable por ruta y por stage.

Una fachada estable

El cliente ve /v1/links para siempre; detrás puedes cambiar la Lambda por un contenedor o partir una función en tres sin que ningún consumidor cambie una línea.

WebSockets sin servidor

La variante WebSocket mantiene las conexiones abiertas por ti y las traduce a invocaciones — chats y dashboards en vivo sin un solo proceso persistente tuyo.

Los tipos que existen

Hay tres productos bajo el mismo nombre, y dos de ellos hacen casi lo mismo. La razón es histórica: REST API (2015) acumuló funcionalidad y precio; HTTP API (2019) es la reescritura barata y rápida con solo lo que casi todo el mundo usa. En el provider de Terraform la frontera es visible: REST API son los recursos aws_api_gateway_* (v1), HTTP y WebSocket son aws_apigatewayv2_*.

El criterio de decisión

Empieza siempre por HTTP API. Pásate a REST API solo cuando puedas nombrar la funcionalidad concreta que te falta — API keys para vender la API, WAF por exigencia de seguridad, caché de respuestas, canary — y acepta que pagas 3,5× por petición por ella. La tabla oficial de diferencias es la fuente; si tu requisito no está en la columna que le falta a HTTP API, no hay debate.

Cómo funciona por dentro

Cuatro piezas que se declaran por separado, y una petición las atraviesa en orden:

  • API — el contenedor. Al crearla, AWS le asigna una URL regional del tipo https://{id}.execute-api.us-east-1.amazonaws.com, con TLS incluido.
  • Ruta — un route key: método + camino, como POST /links o GET /{code}. Las llaves {} capturan parámetros; $default atrapa lo que ninguna ruta reclama.
  • Integración — a dónde va la petición. Para Lambda es AWS_PROXY: la puerta empaqueta la petición HTTP en un evento JSON, invoca, y desempaqueta la respuesta. El contrato de ese evento es el payload format: la versión 2.0 entrega el sobre con rawPath, requestContext.http.method, pathParameters — y el body como string sin parsear. A la vuelta, si tu función devuelve JSON sin statusCode, la puerta infiere un 200; si devuelve {statusCode, headers, body}, obedece.
  • Stage — la publicación. Una configuración de rutas no atiende tráfico hasta que se despliega a un stage; el stage $default con auto_deploy publica cada cambio solo y desaparece de la URL.

Garantías que importan: es síncrono (el cliente espera la respuesta entera), el timeout de integración es 30 segundos y no se puede subir — da igual que tu Lambda admita 15 minutos, la puerta corta antes — y el throttling por defecto es el de la cuenta: 10 000 peticiones/segundo con ráfagas de 5 000. Y una asimetría de permisos que hay que saberse: tu rol IAM dice lo que tu función puede hacer; quién puede invocarla se decide en una política pegada a la propia función (resource-based policy), que es donde API Gateway pide paso.

Lo que sorprende en la factura

Dos cosas. Una: el free tier de API Gateway caduca a los 12 meses de crear la cuenta — no es como el de Lambda o DynamoDB, que son para siempre; a tu escala da igual (mil peticiones son 0,001 USD), pero conviene saber qué columna del free tier estás mirando. Dos: las peticiones se miden en incrementos de 512 KB — una respuesta de 4,5 MB se factura como 9 peticiones. Con JSONs pequeños no lo notarás nunca; sirviendo ficheros, sí.

Cuándo NO usarlo

Úsalo si

  • El backend es Lambda y la API es pública o multi-cliente.
  • Quieres auth, throttling o CORS sin escribirlos tú.
  • El tráfico es variable o bajo: pagar por petición gana.

No lo uses si

  • Solo tú (o un webhook) llamas a una única función — una Lambda Function URL es gratis y son tres líneas.
  • El tráfico es masivo y sostenido: a decenas de millones de peticiones al día, un ALB por horas sale más barato que pagar cada petición.
  • La respuesta tarda más de 30 segundos sí o sí.

En Terraform

ejemplo mínimo — HTTP API delante de una Lambdahcl
resource "aws_apigatewayv2_api" "api" {
  name          = "mi-api"
  protocol_type = "HTTP"          # o "WEBSOCKET"; REST API es otro recurso (v1)
}

resource "aws_apigatewayv2_stage" "default" {
  api_id      = aws_apigatewayv2_api.api.id
  name        = "$default"        # sin sufijo en la URL
  auto_deploy = true              # sin esto, los cambios de rutas NO se publican
}

resource "aws_apigatewayv2_integration" "fn" {
  api_id                 = aws_apigatewayv2_api.api.id
  integration_type       = "AWS_PROXY"
  integration_uri        = aws_lambda_function.fn.invoke_arn
  integration_method     = "POST" # hacia la Lambda siempre es POST
  payload_format_version = "2.0"  # el default del provider es "1.0"
}

resource "aws_apigatewayv2_route" "fn" {
  api_id    = aws_apigatewayv2_api.api.id
  route_key = "POST /links"       # método + espacio + camino, literal
  target    = "integrations/${aws_apigatewayv2_integration.fn.id}"
}

# Sin esto: 500 en el navegador y ni rastro en los logs de la función.
resource "aws_lambda_permission" "api" {
  statement_id  = "AllowInvokeFromHttpApi"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.fn.function_name
  principal     = "apigateway.amazonaws.com"
  source_arn    = "${aws_apigatewayv2_api.api.execution_arn}/*/*"
}
Trampas conocidas
  • payload_format_version por defecto es "1.0" en el provider; la consola crea integraciones con 2.0. Si tu handler espera el sobre 2.0 y no lo fijas, recibirá el formato viejo — y fallará en el primer campo que no exista. Tercer caso de «el default del provider no es tu default», tras x86_64 y PROVISIONED.
  • Olvidar aws_lambda_permission produce un 500 con {"message":"Internal Server Error"} y — aquí la trampa — cero líneas en los logs de la Lambda, porque la Lambda nunca llegó a invocarse. El error solo vive en los access logs del stage, si los activaste.
  • execution_arn ≠ api_endpoint: el primero es el ARN para permisos (arn:aws:execute-api:…), el segundo la URL pública. En source_arn va el primero, con /*/* (stage y ruta).
  • El route_key es literal: "POST /links" con un espacio exacto. "POST/links" o una barra final de más crean una ruta que jamás casará, y nadie te avisa: las peticiones caen en el 404 Not Found de la API.

Comprueba

Pregunta 1 de 4

Acabas de aplicar la puerta, haces el curl y recibes {"message":"Internal Server Error"}. Abres los logs de la función: vacíos, ni siquiera un START. ¿Cuál es el sospechoso número uno?

Pregunta 2 de 4

Te piden vender el acceso a tu API con claves por cliente y límites de peticiones distintos para cada uno. Estás en HTTP API. ¿Qué haces?

Pregunta 3 de 4

Un servicio interno recibe 40 millones de peticiones al día, planas y predecibles, desde otros sistemas tuyos. ¿Qué puerta le pones, pensando en coste?

Pregunta 4 de 4

Tu handler lee event.rawPath y devuelve {statusCode: 201}. En Terraform declaras la integración sin payload_format_version. ¿Qué pasa en producción?
