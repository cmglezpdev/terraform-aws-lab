Qué es

Un servicio gestionado que se planta entre internet y tu backend: termina el TLS, lee el método y la ruta de cada petición (POST /links), y la entrega al destino que tenga configurado — una Lambda, otro servicio de AWS o cualquier URL. No ejecuta tu código: enruta, filtra y traduce. Existe porque una Lambda no es un servidor: no escucha en ningún puerto, solo responde a invocaciones — y la única forma legal de invocarla desde fuera de AWS es que un servicio con permiso lo haga por ti.

La analogía que sí sirve

El recepcionista de un edificio de oficinas: tú no entras a la planta 7 — le dices a quién buscas, él comprueba la lista, llama arriba y te hace pasar o no. Las oficinas ni siquiera tienen puerta a la calle. Donde se rompe: un recepcionista cobra sueldo fijo esté el edificio vacío o lleno; una HTTP API cobra por visita — cero visitas, cero coste. Esa diferencia es exactamente la que hay con un ALB, que sí cobra por hora.

Para qué se usa de verdad

Dar URL pública a una Lambda

Tu caso: el acortador tiene cerebro y memoria, pero nadie de fuera puede llamarlo. La puerta convierte POST /links en una invocación con permiso.

Autenticación sin escribirla

Un authorizer JWT valida los tokens de Cognito o de cualquier OIDC antes de que tu función se ejecute (y pague). El 401 lo pone la puerta, no tu código.

Proteger el backend del pico

Throttling: si alguien te hace 50 000 peticiones por segundo, la puerta devuelve 429 y tu base de datos ni se entera. Configurable por ruta y por stage.

Vender la API por clientes

API keys y usage plans: cada cliente tiene su clave y su cupo («100 000 peticiones al mes, 10 por segundo»). Solo en REST API — es la sección del proyecto 03.

Una fachada estable

El cliente ve /v1/links para siempre; detrás puedes cambiar la Lambda por un contenedor o partir una función en tres sin que ningún consumidor cambie una línea.

WebSockets sin servidor

La variante WebSocket mantiene las conexiones abiertas por ti y las traduce a invocaciones — chats y dashboards en vivo sin un solo proceso persistente tuyo.

Los tipos que existen

Hay tres productos bajo el mismo nombre, y dos de ellos hacen casi lo mismo. La razón es histórica: REST API (2015) acumuló funcionalidad y precio; HTTP API (2019) es la reescritura barata y rápida con solo lo que casi todo el mundo usa. En el provider de Terraform la frontera es visible: REST API son los recursos aws_api_gateway_* (v1), HTTP y WebSocket son aws_apigatewayv2_*.

El criterio honesto de cuándo pagar REST

Empieza siempre por HTTP API. La regla no es «REST tiene más cosas»: es ¿puedes nombrar la fila concreta de esa tabla que te falta? Si no puedes, no hay debate. Si puedes, la pregunta siguiente es cuánto cuesta esa fila:

  • API keys y límites por cliente — la razón nº 1 y la más legítima. Es funcionalidad que si no compras, escribes. Los números, abajo.
  • WAF — pero se puede tener sobre HTTP API poniendo CloudFront delante, así que no es una razón cerrada: es una comparación de dos montajes.
  • Endpoint privado — esa sí es exclusiva y sin rodeo: una API que solo se llama desde dentro de la VPC tiene que ser REST.
  • Caché — cuidado: la caché es la única pieza del servicio que cobra por hora, exista tráfico o no. Ver más abajo antes de quererla.
  • Validación de request y VTL — la más discutible. Validar el body en tu función cuesta 15 líneas y no cuesta 3,5× por petición.

Y el multiplicador, dicho sin adornos: 3,50 frente a 1,00 USD por millón. A un millón de peticiones al mes son 2,50 USD de diferencia — ruido. A cincuenta millones, 125 USD/mes. El multiplicador no decide en pequeño; decide en grande.

Usage plans y API keys: el rate limiting por cliente

La pieza que el proyecto 03 necesita, y la que más claramente separa los dos productos. Un usage plan es un contrato de consumo asociado a stages concretas de una API, con dos números independientes:

  • Throttle — rate_limit (peticiones por segundo en régimen estable) y burst_limit (capacidad del cubo de tokens, o sea el pico instantáneo tolerado). Es el «no me hagas 500 por segundo».
  • Quota — limit peticiones por DAY, WEEK o MONTH. Es el «tu plan son 100 000 al mes».

Una API key es una cadena alfanumérica de 20 a 128 caracteres que el cliente manda en la cabecera x-api-key. La clave identifica al cliente; el plan al que está asociada define sus números. Una clave puede estar en varios planes, y un plan en varias stages, pero una clave solo puede estar en un plan por cada stage.

Lo que la propia AWS advierte, y casi nadie lee
  • Una API key no es autenticación. Textual en la doc: «Don't use API keys for authentication or authorization to control access to your APIs». Van en una cabecera que se loguea, no se firman, y si tienes varias APIs en un mismo plan, una clave válida para una abre todas las del plan. La autenticación va aparte: IAM, Lambda authorizer o Cognito. La clave dice quién consume, no quién es.
  • Los límites son «best-effort», no barreras. También textual: «Usage plan throttling and quotas are not hard limits… In some cases, clients can exceed the quotas that you set. Don't rely on usage plan quotas or throttling to control costs». Si tu objetivo es que nadie te arruine la factura, la herramienta es Budgets y, si hace falta, WAF — no el usage plan.
  • Actualizar un plan tarda. Añadir una clave a un plan «might take a few minutes to complete»: no es un cambio inmediato como una política IAM.

Fuente: Usage plans and API keys for REST APIs, consultada el 2026-08-30.

Lo que los números no dicen, y decide más que ellos:

  • La caché del authorizer te pelea el contador. Si cacheas el resultado 300 segundos, el authorizer no se invoca en cada petición — y entonces no puede contarlas. O cacheas y cuentas aparte (desde la propia función de negocio), o no cacheas y pagas una invocación y una escritura por petición.   • La vuelta atrás. Migrar de HTTP API a REST API no es un flag: es reescribir los recursos de Terraform de v2 a v1, montar deployment, method, integration y method_response, y cambiar el formato del evento que recibe tu handler. Decidirlo ahora es más barato que decidirlo en el proyecto 05.

Authorizers: quién pone el 401

Un authorizer es la pieza que decide, antes de tu integración, si la petición pasa. Que el rechazo ocurra en la puerta importa por dos motivos: tu función no se ejecuta (no paga) y no ve nunca al no autorizado.

La caché del authorizer y sus tres trampas

Un authorizer Lambda se puede cachear: authorizer_result_ttl_in_seconds, que en el provider de Terraform vale 300 por defecto y admite hasta 3 600. Es la diferencia entre invocar una Lambda extra en cada petición y hacerlo una vez cada cinco minutos. Lo que hay que saber antes de activarla:

  • La clave de caché son las identity sources, no el usuario. Si tu identity source es $request.header.Authorization, dos peticiones con el mismo token comparten la respuesta cacheada. Y sin identity sources no hay caché posible: la doc lo dice explícito.
  • Por defecto la respuesta cacheada vale para todas las rutas de la API. Con enable_simple_responses (el booleano isAuthorized), un «sí» cacheado abre todo lo que use ese authorizer. Si quieres permisos por ruta, o añades $context.routeKey a las identity sources, o devuelves una política IAM en vez del booleano.
  • Revocar un token no es inmediato. Con TTL de 300 s, un token que acabas de invalidar sigue entrando hasta cinco minutos. Es un compromiso legítimo — pero hay que tomarlo a propósito, no heredarlo del default del provider.

Dos comportamientos más que explican errores confusos: si el cliente no manda la identity source, API Gateway ni invoca tu authorizer y devuelve 401 directamente; y si API Gateway no tiene permiso para invocar el authorizer, o el authorizer devuelve un formato inválido, el cliente recibe 500 — el mismo síntoma mudo que la Lambda de negocio sin aws_lambda_permission. El authorizer necesita su propio permiso, con source_arn apuntando a …:{api-id}/authorizers/{authorizer-id}.

Fuentes: Lambda authorizers para HTTP APIs y JWT authorizers, consultadas el 2026-08-30.

Detalles del authorizer JWT que ahorran una tarde
  • Solo algoritmos RSA. Un emisor que firme con HS256 (clave simétrica) no sirve: necesitas un authorizer Lambda.
  • La clave pública se cachea dos horas. Al rotar claves en el IdP, deja un periodo de gracia en el que la vieja y la nueva sean válidas.
  • No distingue un access token de un ID token. La propia doc lo dice: «There is no standard mechanism to differentiate JWT access tokens from other types of JWTs». La recomendación de AWS es exigir scopes en la ruta (authorization_scopes) o un aud/iss que tu IdP solo use al emitir access tokens.
  • Las claims llegan a tu handler en event.requestContext.authorizer.jwt.claims — no vuelvas a decodificar el token dentro de la función.

CORS: por qué el curl no se entera

CORS no es una protección del servidor: es una restricción que aplica el navegador. Por eso el síntoma es siempre el mismo desconcierto — tu curl funciona perfecto, y la misma petición desde una web falla con Cross-Origin Request Blocked. El curl no manda cabecera origin y no hace preflight; el navegador sí. Si toda tu verificación es por terminal, CORS es invisible hasta que hay front.

En HTTP API se declara y se acabó: un bloque cors_configuration con allow_origins, allow_methods, allow_headers, expose_headers, max_age y allow_credentials. Con eso, API Gateway responde solo a los OPTIONS de preflight aunque no tengas ninguna ruta OPTIONS. Las dos trampas:

  • Si configuras CORS en la API, API Gateway ignora las cabeceras CORS que devuelva tu integración. Textual en la doc. Elige un sitio: la puerta o tu código. Ponerlo en los dos no duplica — silencia al de abajo, que es peor porque parece que tu código no hace efecto.
  • Ruta $default + authorizer = preflight roto. La ruta $default atrapa también los OPTIONS, y si lleva authorizer, el navegador recibe un 401 en el preflight y ni siquiera intenta la petición real. La solución documentada: añade una ruta OPTIONS /{proxy+} sin autorización — tiene más prioridad que $default.

Un tercer detalle que rompe en producción y no en desarrollo: allow_credentials = true junto a allow_origins = ["*"] es una combinación que el navegador rechaza por especificación. Con credenciales hay que listar orígenes concretos.

Cómo funciona por dentro

Cuatro piezas que se declaran por separado, y una petición las atraviesa en orden:

  • API — el contenedor. Al crearla, AWS le asigna una URL regional del tipo https://{id}.execute-api.us-east-1.amazonaws.com, con TLS incluido.
  • Ruta — un route key: método + camino, como POST /links o GET /{code}. Las llaves {} capturan parámetros; $default atrapa lo que ninguna ruta reclama.
  • Integración — a dónde va la petición. Para Lambda es AWS_PROXY: la puerta empaqueta la petición HTTP en un evento JSON, invoca, y desempaqueta la respuesta. El contrato de ese evento es el payload format: la versión 2.0 entrega el sobre con rawPath, requestContext.http.method, pathParameters — y el body como string sin parsear. A la vuelta, si tu función devuelve JSON sin statusCode, la puerta infiere un 200; si devuelve {statusCode, headers, body}, obedece.
  • Stage — la publicación. Una configuración de rutas no atiende tráfico hasta que se despliega a un stage; el stage $default con auto_deploy publica cada cambio solo y desaparece de la URL.

Garantías que importan: es síncrono (el cliente espera la respuesta entera) y hay una asimetría de permisos que hay que saberse: tu rol IAM dice lo que tu función puede hacer; quién puede invocarla se decide en una política pegada a la propia función (resource-based policy), que es donde API Gateway pide paso.

Stages y deployments: la asimetría que rompe el apply

En los dos productos, una configuración de rutas no atiende tráfico hasta que se publica. La diferencia es quién pulsa el botón:

  • HTTP API: auto_deploy = true en el stage y se acabó. Cada cambio de ruta o integración se publica solo. Es el default sensato que hace que el proyecto 01 no tenga que pensar en esto.
  • REST API: un deployment es una foto inmutable de la configuración, y el stage apunta a una foto. Si cambias un método y no creas un deployment nuevo, Terraform dice Apply complete y la API sigue sirviendo lo viejo. Es el fallo nº 1 de REST API en Terraform, porque no hay error: hay silencio.

El patrón correcto en el provider es triggers + create_before_destroy (ver En Terraform). Sin create_before_destroy, el propio provider avisa de qué se rompe: BadRequestException: Active stages pointing to this deployment must be moved or deleted.

Throttling: cuatro capas, y se aplican en este orden

Hay cuatro techos distintos, y no son alternativas: la petición los cruza todos. El orden en que API Gateway los evalúa, según la doc:

#CapaAlcanceDónde se configura
1Por cliente / por método en un usage planUna API key aws_api_gateway_usage_plan — solo REST
2Por método o por ruta en el stageTodos los clientes de esa ruta route_settings (v2) o aws_api_gateway_method_settings (v1)
3De la cuenta, por regiónTodas tus APIs de la región Service Quotas: 10 000 req/s, ráfaga 5 000
4De AWSToda la región, todas las cuentas No se toca. Es el techo del servicio

El algoritmo es un token bucket: rate es a qué velocidad se rellena el cubo y burst cuántos tokens caben. Por eso un pico corto pasa y uno sostenido no. Cuando se agota, el cliente recibe 429 Too Many Requests, y la doc insiste en que todos estos números son objetivos, no garantías: «Both throttles and quotas are applied on a best-effort basis and should be thought of as targets rather than guaranteed request ceilings».

El límite de cuenta es compartido entre HTTP, REST y WebSocket — una API ruidosa se come el cupo de las demás. El rate se sube por Service Quotas; la ráfaga no: «It is not a quota that a customer can control or request changes to». Y ojo con la región: en trece regiones (Ciudad del Cabo, Milán, Yakarta, Emiratos, Hyderabad, Melbourne, España, Zúrich, Tel Aviv, Calgary, Malasia, Tailandia y México) el default no es 10 000/5 000 sino 2 500/1 250.

La puerta en producción: dominio, logs, caché, privado, mTLS

Dominios propios y ACM

La URL que da AWS (https://a1b2c3d4e5.execute-api.us-east-1.amazonaws.com) sirve para el curso y para nada más: lleva un ID aleatorio y ata tu API a una región visible en el nombre. Un dominio propio son tres piezas: un certificado en ACM, un domain_name en API Gateway, y un API mapping que dice qué stage atiende qué camino base.

La regla que cuesta media hora si no la sabes, textual en la doc:

  • Dominio regional (el de HTTP API, y el recomendado en REST): «you must request or import the certificate in the same Region as your API».
  • Dominio edge-optimized (solo REST): «you must request or import the certificate in the US East (N. Virginia) – us-east-1 Region», porque por debajo es CloudFront.

El certificado público de ACM es gratis y se renueva solo si la validación es por DNS. El dominio propio de API Gateway no tiene coste propio: no hay línea de factura por tenerlo. Y hay un detalle útil para el proyecto 05: puedes desactivar el endpoint por defecto para que nadie siga usando la URL fea — los clientes que insistan reciben 403.

Access logging: el único sitio donde vive el 500 mudo

Los dos productos escriben access logs a CloudWatch Logs: una línea por petición, con el formato que tú definas a base de variables $context. Es literalmente el único lugar donde aparece el error cuando la puerta falla antes de invocar tu función — el 500 por permiso ausente, el authorizer que devolvió basura. Dos variables que conviene meter siempre en el formato:

  • $context.integrationErrorMessage — por qué falló la integración.
  • $context.authorizer.error — por qué falló el authorizer.

Los execution logs (el paso a paso interno de la puerta, con el evento y la respuesta) solo existen en REST API. En HTTP API, lo que no capture el access log no está en ningún sitio.

Los logs no son gratis, y esta es la parte que sorprende

API Gateway no cobra por loguear; CloudWatch Logs sí: 0,50 USD por GB ingerido y 0,03 USD por GB-mes almacenado (Standard, us-east-1, verificado el 2026-08-30 contra la Price List API). Una línea JSON de access log ronda los 400 bytes: un millón de peticiones ≈ 0,4 GB ≈ 0,20 USD/mes — comparable a lo que cuesta la propia HTTP API. Y el almacenamiento es para siempre si no pones retención: exactamente la misma trampa que los logs de Lambda. retention_in_days en el log group, siempre. Los detalles, en la ficha de CloudWatch.

La factura fantasma

Un stage de pruebas con caché de 0,5 GB, olvidado un mes sin una sola petición, factura 14,60 USD. La API no cobra nada, la Lambda no cobra nada, DynamoDB no cobra nada — y llega un cargo que no cuadra con ningún tráfico. Si activas caché, apúntalo en el destroy del proyecto.

APIs privadas y VPC endpoints

Una private API es una REST API que solo se puede llamar desde dentro de una VPC, a través de un interface VPC endpoint (AWS PrivateLink). No tiene URL pública que valga: el tráfico no sale de la red de Amazon. Lo que hay que saber:

  • Solo REST API. Textual: «Only REST APIs are supported». Si necesitas una API privada, la decisión HTTP vs REST está tomada por ti.
  • El endpoint no basta: hace falta la resource policy. Sin una política con condición aws:SourceVpc o aws:SourceVpce, tu API privada es invocable desde cualquier VPC endpoint de cualquier cuenta que la conozca.
  • El DNS privado tiene efecto colateral. Al activarlo en la VPC, dejas de poder resolver los endpoints por defecto de las APIs públicas desde esa VPC. Se arregla con una hosted zone privada por API, pero hay que saberlo antes.
  • No es gratis. El PrivateLink cobra por hora: ~0,01 USD/h por zona de disponibilidad más ~0,01 USD/GB procesado. Dos AZ ≈ 14,60 USD/mes exista o no tráfico. Otra línea por horas que apuntar.
  • Y dos detalles finos: las APIs privadas solo aceptan TLS 1.2, y una API privada no se puede convertir en edge-optimized.

mTLS: el cliente también enseña certificado

TLS mutuo significa que, además de que tú demuestres ser quien dices, el cliente presenta un certificado y tú lo validas. Lo tienen los dos productos — es la fila de la tabla que más gente da por perdida en HTTP API — y se configura en el dominio propio, no en la API: un truststore (un fichero PEM con las CAs que aceptas) subido a S3, y su versión. Límite: 1 000 certificados y 1 MB por truststore. Para actualizarlo, subes una versión nueva del objeto S3 y apuntas el dominio a ella — de ahí que el bucket necesite versionado.

Cuándo importa: integraciones B2B y sectores regulados donde «el cliente es una empresa con su PKI», no un usuario con contraseña. Los datos del certificado llegan a tu authorizer en requestContext.authentication.clientCert.

Response streaming en REST API (novedad de nov-2025)

Si tu conocimiento de este servicio es de 2024, esta parte está desactualizada en tu cabeza: hasta 2025, «quiero que la respuesta llegue por trozos» significaba Lambda Function URL, porque API Gateway siempre esperaba la respuesta entera. Desde noviembre de 2025, REST API soporta responseTransferMode = STREAM en integraciones AWS_PROXY y HTTP_PROXY. Lo que compra:

  • Time-to-first-byte bajo en chatbots y SSE, y ficheros grandes sin URL prefirmada.
  • Se salta los dos límites duros: los 10 MB de payload de respuesta y los 29 segundos de timeout. En streaming puedes emitir hasta 15 minutos.

Lo que cuesta: HTTP API no lo tiene (solo REST, a 3,50 USD/millón); desactiva la caché, la compresión y la transformación VTL; los primeros 10 MB van sin restricción de ancho de banda y a partir de ahí te limita a 2 MB/s; el idle timeout es de 5 minutos en regional y privada, pero de 30 segundos en edge-optimized; y las respuestas en streaming se facturan en incrementos de 10 MB. Request streaming (subida por trozos) sigue sin existir.

Developer portal gestionado (novedad de nov-2025)

Otra pieza nueva que conviene conocer aunque no la uses: API Gateway ahora ofrece portales gestionados donde tus clientes descubren, prueban y se suscriben a tus APIs. Es la funcionalidad que antes había que montarse con una plantilla. El precio la sitúa sola en su sitio: 125,00 USD/mes por portal más 12,50 USD/mes por producto publicado (Price List API, us-east-1, 2026-08-30). No es una pieza de proyecto personal; es una pieza de «vendo mi API a terceros».

Lo que sorprende en la factura

Cuatro cosas. Una: el free tier de API Gateway caduca a los 12 meses de crear la cuenta — no es como el de Lambda o DynamoDB, que son para siempre; a tu escala da igual (mil peticiones son 0,001 USD), pero conviene saber qué columna del free tier estás mirando. Dos: las peticiones se miden en incrementos de 512 KB — una respuesta de 4,5 MB se factura como 9 peticiones (y las respuestas en streaming, en incrementos de 10 MB). Con JSONs pequeños no lo notarás nunca; sirviendo ficheros, sí. Tres: la caché y el portal cobran por tiempo, no por uso — son las dos únicas líneas del servicio que siguen corriendo con la API dormida. Y cuatro: los access logs se pagan en CloudWatch, no aquí, y a un millón de peticiones pueden costar tanto como la propia puerta.

Cuándo NO usarlo

Úsalo si

  • El backend es Lambda y la API es pública o multi-cliente.
  • Quieres auth, throttling o CORS sin escribirlos tú.
  • El tráfico es variable o bajo: pagar por petición gana.

No lo uses si

  • Solo tú (o un webhook) llamas a una única función — una Lambda Function URL es gratis y son tres líneas.
  • El tráfico es masivo y sostenido: a decenas de millones de peticiones al día, un ALB por horas sale más barato que pagar cada petición.
  • La respuesta tarda más de 30 segundos y no puedes usar streaming ni asincronía.

Trampas conocidas
  • payload_format_version por defecto es "1.0" en el provider; la consola crea integraciones con 2.0. Si tu handler espera el sobre 2.0 y no lo fijas, recibirá el formato viejo — y fallará en el primer campo que no exista. Tercer caso de «el default del provider no es tu default», tras x86_64 y PROVISIONED.
  • Olvidar aws_lambda_permission produce un 500 con {"message":"Internal Server Error"} y — aquí la trampa — cero líneas en los logs de la Lambda, porque la Lambda nunca llegó a invocarse. El error solo vive en los access logs del stage, si los activaste.
  • El authorizer necesita su propio permiso. Es una segunda Lambda y una segunda política de recurso, con source_arn apuntando a {execution_arn}/authorizers/{id}. El síntoma de olvidarlo es idéntico: 500 y silencio.
  • execution_arn ≠ api_endpoint: el primero es el ARN para permisos (arn:aws:execute-api:…), el segundo la URL pública. En source_arn va el primero, con /*/* (stage y ruta).
  • El route_key es literal: "POST /links" con un espacio exacto. "POST/links" o una barra final de más crean una ruta que jamás casará, y nadie te avisa: las peticiones caen en el 404 Not Found de la API.
  • En REST API, un deployment sin triggers es una foto congelada. Terraform no ve que cambiaste un método porque el deployment no depende de él: hay que forzarlo con triggers y create_before_destroy. Es el equivalente v1 de olvidar auto_deploy, pero silencioso.
  • authorizer_result_ttl_in_seconds vale 300 por defecto. Si no lo fijas, tu authorizer cachea cinco minutos — y con enable_simple_responses ese «sí» cacheado vale para todas las rutas de la API. Ponlo a 0 mientras desarrollas, o te volverás loco depurando permisos que «no cambian».
  • El certificado ACM del dominio tiene región obligatoria: la de la API si el dominio es regional, us-east-1 si es edge-optimized. El error de Terraform en este caso es genérico y no menciona la región.
