Terraform: CLI y HCL de un vistazo

Lo que consultas a diario. Verificado contra Terraform 1.15 y el provider AWS 6.x.

Ciclo de vida

Los cinco comandos

terraform init      # descarga providers
terraform fmt       # formatea el HCL
terraform validate  # sintaxis y tipos
terraform plan      # calcula el diff
terraform apply     # ejecuta el diff
terraform destroy   # lo borra todo

init se ejecuta al empezar y cada vez que cambies providers o backend. fmt y validate, antes de cada commit.

Símbolos del plan

+crear
-destruir
~modificar en sitio
-/+destruir y recrear — peligroso
<=leer (data source)

-/+ aparece cuando cambias un atributo que AWS no permite modificar (forces replacement). Si sale junto a una base de datos, para.

Flags que se usan de verdad

plan -out=tf.plan     # guarda el plan
apply tf.plan         # aplica ESE plan exacto
apply -auto-approve   # sin preguntar (solo CI)
plan -destroy         # qué haría destroy
-target=aws_s3_bucket.x  # solo un recurso
-var-file=prod.tfvars
-refresh=false        # no consultar AWS

-target es una válvula de emergencia, no una forma de trabajar. Deja el state parcialmente aplicado.

Inspeccionar el state

terraform state list
terraform state show ADDR
terraform show           # todo el state
terraform show -json     # legible por máquina
terraform output
terraform output -raw NOMBRE

Una dirección es tipo.nombre, con ["clave"] si viene de for_each o [0] si viene de count.

Cirugía sobre el state

terraform state mv A B    # renombrar
terraform state rm ADDR   # olvidar (no borra)
terraform import ADDR ID  # adoptar existente
terraform force-unlock ID # lock colgado

state rm hace que Terraform olvide el recurso: sigue existiendo en AWS y ya nadie lo gestiona. Es como se crean los huérfanos que pagas.

Workspaces

terraform workspace list
terraform workspace new dev
terraform workspace select prod

Un state separado por workspace, mismo código. Sirve para entornos efímeros; para dev/prod de verdad se prefieren directorios separados (lo veremos en el proyecto 07).

Bloques del lenguaje

terraform — configuración global

terraform {
  required_version = ">= 1.9"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
  backend "s3" { ... }
}

No admite variables: se evalúa antes que nada.

resource — algo que creas

resource "aws_s3_bucket" "logs" {
  bucket = "mi-bucket-de-logs"
}

# referencia:
aws_s3_bucket.logs.arn

Referenciar un recurso desde otro crea una dependencia implícita. Es la forma correcta; depends_on es el último recurso.

data — algo que consultas

data "aws_caller_identity" "yo" {}
data "aws_region" "actual" {}

# referencia (lleva "data." delante):
data.aws_caller_identity.yo.account_id

No crea nada, no aparece en el destroy, y se resuelve durante el plan. Lee lo que ya existe, dentro o fuera de tu Terraform.

Ojo: no todos consultan AWS. aws_iam_policy_document no llama a ninguna API: es una función local que convierte HCL en JSON, disfrazada de data source porque el lenguaje no tenía otra forma de expresarlo. Lo mismo pasa con archive_file. Si un data source no necesita credenciales, es de estos.

variable — entrada

variable "instance_count" {
  description = "Cuántas instancias."
  type        = number
  default     = 2

  validation {
    condition     = var.instance_count <= 4
    error_message = "Máximo 4, por coste."
  }
}

Siempre type y description. Sin default, es obligatoria.

output — salida

output "api_url" {
  description = "URL pública de la API."
  value       = aws_apigatewayv2_api.x.api_endpoint
  sensitive   = false
}

Es la interfaz pública de un módulo. sensitive = true lo oculta en la consola — pero no en el state.

locals — valores calculados

locals {
  name_prefix = "${var.project}-${var.env}"
  common_tags = {
    Environment = var.env
  }
}

# referencia:
local.name_prefix

Nombre en plural al declarar (locals), en singular al usar (local.).

module — código reutilizable

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
  name    = "principal"
}

# referencia:
module.vpc.private_subnets

Fija version siempre que el source sea remoto.

provider con alias

provider "aws" {
  alias  = "virginia"
  region = "us-east-1"
}

resource "aws_acm_certificate" "cdn" {
  provider = aws.virginia
}

Necesario para multi-región. Los certificados de CloudFront tienen que estar en us-east-1.

Meta-argumentos

for_each vs count

# for_each: clave estable
resource "aws_sqs_queue" "q" {
  for_each = toset(["pedidos", "emails"])
  name     = each.key
}
# → aws_sqs_queue.q["pedidos"]

# count: índice frágil
resource "aws_instance" "web" {
  count = 3
}
# → aws_instance.web[0]

Usa for_each casi siempre. Con count, borrar el elemento del medio reindexa los siguientes y Terraform destruye y recrea recursos que no habías tocado. Con for_each la clave no se mueve.

depends_on

resource "aws_lambda_function" "f" {
  depends_on = [
    aws_iam_role_policy_attachment.logs
  ]
}

Solo para dependencias que Terraform no puede ver: típicamente permisos IAM que deben existir antes aunque nada los referencie.

lifecycle

lifecycle {
  create_before_destroy = true
  prevent_destroy       = true
  ignore_changes        = [tags["LastScan"]]
  replace_triggered_by  = [null_resource.x]
}

prevent_destroy en producción sobre bases de datos. ignore_changes para lo que modifica otro sistema.

dynamic — bloques repetidos

dynamic "ingress" {
  for_each = var.puertos
  content {
    from_port = ingress.value
    to_port   = ingress.value
    protocol  = "tcp"
  }
}

Para repetir bloques anidados, no recursos. Típico en security groups.

Expresiones y funciones

Sintaxis frecuente

"${var.a}-${var.b}"       # interpolación
var.env == "prod" ? 3 : 1  # condicional
[for s in var.l : upper(s)]        # for de lista
{ for k, v in var.m : k => v.id }  # for de mapa
var.x != null ? var.x : "def"
try(var.x.y, "por defecto")

Funciones que usarás

toset(["a","b"])     # lista → set
merge(a, b)          # une mapas
lookup(m, "k", "def")
coalesce(a, b, c)    # primer no-nulo
join("-", lista)
jsonencode({ a = 1 })
file("${path.module}/x.json")
cidrsubnet("10.0.0.0/16", 8, 3)

cidrsubnet es la que te calcula las subredes en el proyecto 04.

Restricciones de versión

~> 6.0cualquier 6.x, nunca 7.0
~> 6.1.0cualquier 6.1.x, nunca 6.2
>= 1.9esa o superior, sin techo
= 6.61.0exactamente esa

Para providers, ~> con la versión mayor fijada.

Valores del entorno

path.module   # dir del módulo actual
path.root     # dir del módulo raíz
terraform.workspace
each.key / each.value   # for_each
count.index             # count

Backend S3 — la forma actual

Con bloqueo nativo, sin DynamoDB

terraform {
  backend "s3" {
    bucket       = "tf-state-999999999999"
    key          = "00-foundations/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true      # ← bloqueo nativo de S3
  }
}

Aviso importante: casi todo el material que encuentres en internet (cursos, blogs, respuestas de Stack Overflow) te dirá que uses dynamodb_table = "..." para el bloqueo. Eso está deprecado y desaparecerá en una versión futura: el bloqueo por DynamoDB se sustituyó por un fichero de lock en el propio bucket. (docs del backend s3)

Un backend no admite variables ni interpolación. Si necesitas que cambie por entorno, se pasa por línea de comandos: terraform init -backend-config=prod.hcl.

Cuando no sabes qué valores acepta un argumento

El autocompletado del editor sabe que budget_type es un string obligatorio, pero no sabe que solo acepta seis valores. No es un fallo de la extensión: el esquema que el provider le entrega solo lleva el tipo, nunca la lista de valores válidos. Esa lista vive en código, dentro del binario del provider. De ahí que haya que sacarla de otro sitio.

1. Escribe mal a propósito

El truco más rápido, y no necesita credenciales ni tocar AWS:

budget_type = "MONEY"   # inventado

terraform validate
Error: expected budget_type to be one of
["USAGE" "COST" "RI_UTILIZATION" "RI_COVERAGE"
 "SAVINGS_PLANS_UTILIZATION"
 "SAVINGS_PLANS_COVERAGE"], got MONEY

El provider te enumera los valores válidos en el propio error. Funciona con cualquier argumento que tenga lista cerrada. Es tu autocompletado real.

2. Pregunta al esquema

Para saber qué argumentos existen, si son obligatorios y de qué tipo, sin abrir el navegador:

terraform providers schema -json \
  | jq '.provider_schemas
        | .[].resource_schemas
        | .aws_budgets_budget.block.attributes'

Es la verdad absoluta sobre tu versión exacta del provider. Lo que no trae —nunca— son los valores permitidos.

3. La documentación en crudo

La web del Registry es una SPA y se lee mal. El mismo contenido, en texto:

https://raw.githubusercontent.com/
  hashicorp/terraform-provider-aws/main/
  website/docs/r/RECURSO.html.markdown

Sustituye RECURSO sin el prefijo aws_: budgets_budget, iam_user. Cámbialo por d/ en vez de r/ para los data sources.

4. El nombre de la acción IAM

Para actions = [...] no hay esquema que valga: son las operaciones de la API de cada servicio. La lista canónica, servicio a servicio:

https://docs.aws.amazon.com/service-authorization/
  latest/reference/reference_policy_actions-resources
  -contextkeys.html

Trae además qué ARN admite cada acción y qué claves de condición. Es la única fuente que no se inventa nada.

Cuando no sabes qué recursos hacen falta

El problema anterior era «no sé qué valores acepta este argumento». Este es peor: no sé cuántos recursos necesito ni cómo se enganchan. Pasa con cada servicio nuevo de AWS, y es exactamente lo que la consola te escondía — porque la consola crea recursos que nunca te enseña.

La técnica: constrúyelo con clics una vez, y luego pide que te escriban el código. Es un bucle de retroalimentación que puedes cerrar solo, sin tutoriales.

Paso 1 — Interroga a AWS con la CLI

Antes de Terraform. Empiezas por la cosa que sabes que existe y vas tirando del hilo. Con una Lambda creada a mano en la consola:

terminaltirar del hilo
FN=mi-funcion-de-prueba

# 1. Toda la configuración de la función. Léela entera:
#    Role, Runtime, Handler, MemorySize, Timeout, Architectures,
#    CodeSha256, LoggingConfig...
aws lambda get-function-configuration --function-name "$FN"

# 2. ¿Qué rol le puso la consola? Nunca lo elegiste tú.
ROLE=$(aws lambda get-function-configuration --function-name "$FN" \
        --query Role --output text)
ROLE=${ROLE##*/}
echo "$ROLE"    # p.ej. mi-funcion-de-prueba-role-a1b2c3d4

# 3. La política de CONFIANZA: quién puede SER ese rol.
#    Aquí verás lambda.amazonaws.com y sts:AssumeRole.
aws iam get-role --role-name "$ROLE" --query AssumeRolePolicyDocument

# 4. Las políticas de IDENTIDAD: qué puede HACER. Son dos listas
#    distintas y hay que mirar las dos.
aws iam list-attached-role-policies --role-name "$ROLE"   # gestionadas
aws iam list-role-policies          --role-name "$ROLE"   # inline

# 5. El contenido de la gestionada que la consola engancha sola.
#    Fíjate en el Resource: es "*".
P=arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
aws iam get-policy-version --policy-arn "$P" \
  --version-id "$(aws iam get-policy --policy-arn "$P" \
                   --query Policy.DefaultVersionId --output text)" \
  --query 'PolicyVersion.Document'

# 6. El grupo de logs que nadie declaró. Mira si sale
#    retentionInDays: si no aparece, es "no expira nunca".
aws logs describe-log-groups --log-group-name-prefix "/aws/lambda/$FN"

# Y la lista completa de huérfanos de tu cuenta:
aws logs describe-log-groups \
  --query 'logGroups[?!retentionInDays].[logGroupName,storedBytes]' \
  --output table

Paso 2 — Que Terraform te escriba el HCL

Con los nombres que acabas de descubrir, un directorio de usar y tirar, un bloque import por recurso, y ningún fichero de recurso. Disponible desde Terraform 1.5.

Sigue marcado como experimental: terraform plan -help lo lista como «(Experimental) If import blocks are present in configuration…», también en 1.15.8. En la práctica significa que el formato del fichero generado puede cambiar entre versiones menores — que da igual, porque lo que haces con él es leerlo, no versionarlo.

terminaldirectorio desechable
mkdir -p /tmp/autopsia && cd /tmp/autopsia

cat > versions.tf <<'EOF'
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}
provider "aws" { region = "us-east-1" }
EOF

cat > imports.tf <<EOF
import {
  to = aws_lambda_function.probe
  id = "$FN"
}

import {
  to = aws_iam_role.probe
  id = "$ROLE"
}

import {
  to = aws_cloudwatch_log_group.probe
  id = "/aws/lambda/$FN"
}
EOF

terraform init
terraform plan -generate-config-out=descubierto.tf

cat descubierto.tf   # ← aquí está todo lo que la consola hizo por ti
Cómo se escribe el id de cada recurso

No es adivinable: cada recurso define el suyo, y está al final de su página de documentación, en la sección Import. Los del ejemplo:

Recursoid de import
aws_lambda_functionel function_name
aws_iam_roleel name del rol
aws_cloudwatch_log_groupel name, con sus barras
aws_iam_role_policynombre_del_rol:nombre_de_la_politica

Para verlo de cualquier otro recurso, usa la doc en crudo de la sección anterior y busca «terraform import» al final.

Tres cosas que hay que tener claras antes de ejecutarlo

1. plan no toca nada. Es de solo lectura: consulta la API y escribe un fichero en tu disco. Lo que sí importaría los recursos a este state es un apply, y en un directorio de autopsia no lo ejecutes nunca: un destroy posterior te borraría la Lambda de verdad. Mira, copia lo que te sirva, y rm -rf /tmp/autopsia.

2. El código generado es un borrador, no un ejemplo a seguir. Trae todos los atributos que devuelve la API, incluidos los que tienen valor por defecto y los de solo lectura. HashiCorp lo dice: es «la mejor conjetura de Terraform», y con esquemas complejos puede generar argumentos mutuamente excluyentes que hay que borrar a mano. Sirve para leer, no para copiar y pegar.

3. Los nombres de recurso son tuyos. aws_iam_role.probe es una etiqueta que eliges tú; el id es lo que identifica la cosa en AWS. No los confundas.

Qué buscar en descubierto.tf

No lo leas entero. Busca estas cuatro cosas, que son las que la consola no te enseñó:

  • El assume_role_policy del rol, con lambda.amazonaws.com dentro. Esa es la política de confianza que nunca escribiste.
  • Si el aws_cloudwatch_log_group tiene retention_in_days. No lo tendrá.
  • El architectures: será ["x86_64"], porque es el defecto y nadie te preguntó.
  • El timeout: será 3, el defecto, casi nunca lo que querías.

Repite este ejercicio con el primer servicio de AWS que no entiendas. Funciona con todos.

Cuando algo va mal

«Error acquiring the state lock»

Un apply anterior murió sin soltar el lock. Copia el ID del mensaje de error y:

terraform force-unlock ID

Antes de hacerlo, asegúrate de que nadie más está aplicando. Es exactamente la situación que el lock existe para evitar.

«already exists»

El recurso existe en AWS pero no en tu state. Lo adoptas en vez de recrearlo:

terraform import aws_s3_bucket.x mi-bucket

O en Terraform ≥ 1.5, con un bloque import en el código, que además te deja verlo en el plan antes de ejecutarlo.

Un plan propone cambios que no pediste

Es drift: alguien tocó AWS a mano, o el provider cambió de versión. Diagnóstico:

terraform plan -refresh-only

Muestra qué ha cambiado en la realidad, sin proponer tocarla.

Ver qué hace Terraform por dentro

TF_LOG=DEBUG terraform apply
TF_LOG=TRACE TF_LOG_PATH=tf.log terraform apply

Verboso hasta lo absurdo, pero es la única forma de ver las llamadas HTTP reales a la API de AWS cuando un error no tiene sentido.
