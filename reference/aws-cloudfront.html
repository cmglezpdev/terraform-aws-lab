Amazon CloudFront

La CDN de AWS: cientos de edge locations repartidas por el mundo guardan copias de tu contenido y responden desde la más cercana al visitante. Pero el producto real no es «va más rápido»: es que el borde se convierte en la única puerta de tu aplicación — TLS, dominio propio, WAF, control de acceso y caché dejan de vivir en el origen, y el origen deja de estar expuesto.

Qué es

Un proxy inverso cacheante desplegado en cientos de centros de datos (los edge locations o POPs). Tú declaras una distribución: de dónde sacar el contenido (los origins), qué reglas aplicar según la ruta pedida (los cache behaviors) y con qué dominio y certificado atender a los visitantes. CloudFront replica esa configuración —no tu contenido— a todos sus POPs, y a partir de ahí cada POP resuelve por su cuenta: si tiene el objeto fresco lo devuelve; si no, lo pide al origen por la red troncal de AWS, lo guarda y lo devuelve.

Existe porque un origen único tiene tres problemas a la vez —latencia para el que está lejos, carga proporcional al tráfico, y exposición directa a internet— y los tres se resuelven con la misma pieza: alguien delante que responda por él.

La analogía que sí sirve

Una cadena de librerías con un único almacén central. Cada tienda pide al almacén el libro que le falta, se queda una copia en la estantería, y el siguiente cliente se lo lleva sin que el almacén se entere. Donde se rompe: las tiendas no se hablan entre ellas. Que Madrid tenga el libro no significa que Tokio lo tenga; cuando publicas una versión nueva, el almacén no llama a nadie — cada tienda se entera cuando su copia caduca. Por eso «invalidar» es una operación explícita y no gratis del todo, y por eso el truco profesional no es invalidar sino cambiarle el nombre al libro.

Para qué se usa de verdad

Servir un SPA desde un bucket privado

Tu caso, el proyecto 05: S3 guarda el index.html y los bundles, CloudFront pone el dominio, el certificado y la caché, y el bucket no tiene ni una política pública. Sin CloudFront tendrías que abrir el bucket a internet y renunciar a HTTPS con dominio propio.

Quitarle el 90 % del tráfico al origen

Un ALB con dos instancias que aguantaba 500 req/s pasa a recibir 50: el resto lo sirve el borde. No es optimización prematura — es la diferencia entre escalar el cómputo y no escalarlo.

Poner TLS y WAF delante de una API

Certificado gestionado, política de TLS mínima, reglas de AWS WAF y restricción por país aplicadas antes de que la petición entre en tu región. El origen solo ve lo que sobrevivió.

Esconder un ALB o una EC2 en subred privada

Con VPC origins (2024) el balanceador deja de tener IP pública: CloudFront entra por un enlace privado y es la única entrada posible. Adiós a las listas de rangos IP que había que mantener a mano.

Distribuir descargas o vídeo con control de acceso

URLs y cookies firmadas con caducidad: el fichero está en un bucket privado y solo lo sirve el borde a quien tu aplicación autorizó, sin que tu backend transfiera un solo byte.

El modelo: distribución, origins, behaviors, edge locations

Cuatro piezas y una regla de precedencia. Casi todos los errores de configuración salen de no tener este orden claro:

diagramade la petición al origen
  visitante
     │  https://app.example.com/api/users?page=2
     ▼
  ┌──────────────── edge location más cercana ────────────────┐
  │ 1. TLS con TU certificado (ACM, us-east-1)                │
  │ 2. ¿qué CACHE BEHAVIOR casa con la ruta /api/users?       │
  │      /api/*   ─── behavior 1  (el primero que casa gana)  │
  │      /static/* ── behavior 2                              │
  │      *        ─── default_cache_behavior (siempre último) │
  │ 3. el behavior fija: origen, cache policy, TTLs,          │
  │    métodos permitidos, funciones edge, compresión         │
  │ 4. ¿está el objeto en caché bajo su CACHE KEY?            │
  │      sí → responde (X-Cache: Hit from cloudfront)         │
  │      no → 5                                               │
  └───────────────────────────┬───────────────────────────────┘
                              │ red troncal de AWS
                              ▼
                       ORIGIN (S3 / ALB / VPC origin / HTTP)
  • Los behaviors se evalúan en orden y gana el primero que casa. No es «el más específico»: es el orden de la lista. Si pones * el primero, los demás no se ejecutan jamás. En Terraform el default_cache_behavior es siempre el último y el que atrapa lo que nadie quiso.
  • El cache key decide si hay hit. Por defecto es solo la ruta. Todo lo que añadas (una query string, una cabecera, una cookie) multiplica el número de copias que el borde debe guardar y divide tu hit ratio. Cachear peor es la forma más habitual de gastar más y ir más lento a la vez.
  • Cada POP cachea por su cuenta. No hay caché global compartida. Un objeto poco pedido en un POP puede ser desalojado antes de caducar para hacer sitio a otro más popular.
  • El objeto viaja por la red de AWS, no por internet. Esa es la mitad de la mejora de latencia; la otra mitad es no cruzar el océano en absoluto.

Qué es global y qué es regional aquí

CloudFront es de los pocos servicios de AWS con ámbito global: la distribución no vive en una región, y en la consola aparece con la región fijada a us-east-1 porque ahí está su plano de control. Consecuencias prácticas que sorprenden:

  • El certificado ACM debe estar en us-east-1 aunque tu bucket y tu equipo estén en eu-west-1. Es la razón por la que el proyecto 05 introduce provider con alias. Detalle abajo, en el requisito de us-east-1.
  • La web ACL de AWS WAF para CloudFront también se crea con scope CLOUDFRONT en us-east-1.
  • Las métricas de CloudWatch de una distribución están en us-east-1, no en tu región.
  • Los logs y las invalidaciones son globales.

La distinción global / regional / zonal, con el mapa completo de qué cae en cada cubo, está en la ficha de fundamentos de AWS.

OAC vs OAI: el patrón del proyecto 05

El problema: quieres que el bucket sea privado y que solo CloudFront pueda leerlo. La solución vigente se llama Origin Access Control (OAC). La anterior se llama Origin Access Identity (OAI), es legacy, y media internet la sigue enseñando — incluido el ejemplo del propio provider de Terraform, que aún usa s3_origin_config con OAI.

La pieza que la gente olvida: crear el OAC no da permiso a nada. El permiso vive en la política del bucket, y la condición AWS:SourceArn es lo que impide que cualquier distribución de cualquier cuenta de AWS lea tu bucket por el mero hecho de que el principal sea el servicio CloudFront.

política de bucketjson — la que recomienda AWS
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::mi-bucket/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E1234ABCDEF"
      }
    }
  }]
}
Las tres trampas del OAC
  • Sin AWS:SourceArn, el bucket es de todo el mundo. El principal cloudfront.amazonaws.com lo comparten todas las cuentas de AWS. Un Allow sin condición es, en la práctica, un bucket público con pasos extra.
  • signing_behavior tiene que ser always. Con never el OAC no firma nada y el bucket tendría que ser público; con no-override solo firma cuando el visitante no mandó Authorization. Además, solo con always el tramo CloudFront→S3 va siempre por HTTPS.
  • El bucket debe tener Object Ownership en BucketOwnerEnforced (el valor por defecto en buckets nuevos: ACLs desactivadas). Y no puede ser un website endpoint: ahí el OAC no aplica.

Ciclo de dependencias: la política del bucket necesita el ID de la distribución, y la distribución necesita el bucket. Terraform lo resuelve sin ayuda porque aws_cloudfront_distribution no depende de aws_s3_bucket_policy — crea primero la distribución (con el bucket como origen) y después la política. Durante los ~15 minutos del despliegue verás 403; es normal.

Cómo funciona por dentro: caché, TTLs e invalidaciones

Las policies modernas frente a forwarded_values

CloudFront separó en 2020 lo que antes era un solo bloque confuso. Hoy hay tres policies por behavior, cada una con su propio recurso Terraform y con versiones managed (creadas y mantenidas por AWS, gratis, con ID fijo):

PolicyQué decideManaged útil
Cache policy
aws_cloudfront_cache_policy		 Qué entra en el cache key (query strings, headers, cookies) y los TTL mínimo, máximo y por defecto. Lo que entra aquí también se reenvía al origen. CachingOptimized (nada en la clave salvo la ruta, compresión activada) — el correcto para un frontend estático.
CachingDisabled para rutas dinámicas.
Origin request policy
aws_cloudfront_origin_request_policy		 Qué se reenvía al origen sin formar parte del cache key. Es la respuesta a «necesito la cabecera pero no quiero fragmentar la caché». AllViewerExceptHostHeader para orígenes tipo ALB o API Gateway.
Response headers policy
aws_cloudfront_response_headers_policy		 Cabeceras que CloudFront añade a la respuesta sin tocar el origen: CORS, HSTS, CSP, X-Frame-Options. SecurityHeadersPolicy: te da las cabeceras de seguridad sin escribir una línea en el bucket.
Internet te va a enseñar forwarded_values

El bloque forwarded_values { query_string, cookies, headers } es el mecanismo legacy. Está marcado Deprecated en el provider de AWS («use cache_policy_id or origin_request_policy_id instead»), y AWS lo lista como legacy feature incompatible con los planes de tarifa plana. Lo malo: el ejemplo principal de la documentación del propio recurso aws_cloudfront_distribution todavía lo usa, y de ahí lo copia la mitad de los blogs. Si ves forwarded_values en un tutorial, el tutorial es de antes de 2021 aunque tenga fecha de ayer.

TTLs contra Cache-Control: quién manda

Sin cache policy, el TTL por defecto es 24 horas. Con policy, los tres valores (mínimo, por defecto, máximo) negocian con lo que diga el origen. La tabla completa, resumida a lo que necesitas:

El origen manda…Con TTL mínimo = 0Con TTL mínimo > 0
Cache-Control: max-age=N Cachea el menor entre N y el TTL máximo Se recorta a mínimo y máximo: si N está entre ambos, gana N
Nada Cachea el TTL por defecto El mayor entre TTL mínimo y TTL por defecto
max-age + s-maxage CloudFront obedece a s-maxage; el navegador a max-age Igual, recortado a mínimo/máximo
no-cache / no-store / private CloudFront y navegador los respetan Los ignora y cachea el TTL mínimo ⚠️

Esa última fila es la trampa cara: un TTL mínimo > 0 anula el no-store de tu origen. Si vas a servir algo verdaderamente privado por una ruta, usa la managed CachingDisabled, no un TTL mínimo «pequeñito».

CloudFront también entiende stale-while-revalidate (sirve la copia caducada mientras refresca en segundo plano) y stale-if-error (sigue sirviendo si el origen devuelve 5xx). Ambos se limitan al TTL máximo del behavior, gane quien gane.

Invalidaciones vs nombres versionados

Las primeras 1 000 rutas de invalidación al mes son gratis por cuenta (no por distribución); a partir de ahí, 0,005 USD por ruta. Un /* cuenta como una ruta. Suena a que invalidar es gratis, y para un proyecto pequeño lo es. Pero AWS recomienda explícitamente lo contrario, y las razones son buenas:

Nombres versionados (app.7f3a1c.js)

  • Controlas también las cachés que no son tuyas: el navegador y el proxy corporativo. Invalidar el borde no vacía el navegador del usuario.
  • Puedes tener dos versiones vivas a la vez: rollback instantáneo, despliegues canary.
  • Los access logs distinguen qué versión sirvió qué.
  • Es gratis y no tiene latencia de propagación.

Invalidación

  • Es la herramienta correcta para el puñado de ficheros que no pueden llevar hash: index.html, manifest.json, sitemap.xml.
  • Tarda en propagarse a todos los POPs (minutos).
  • Cuota de ritmo: 150 rutas o tags por segundo; una sola invalidación comodín por segundo.

La receta honesta para el proyecto 05: que el build ponga hash en el nombre de todos los assets, súbelos con Cache-Control: max-age=31536000, immutable, y deja el index.html con max-age=0, must-revalidate invalidando solo /index.html en cada deploy. Un fichero por deploy: 1 000 despliegues gratis al mes.

Novedad reciente: además de rutas, ahora se puede invalidar por cache tags (marcas que el origen pone en la respuesta), lo que permite tirar un grupo lógico de objetos sin enumerar rutas. Comparte la cuota de 150/segundo.

El criterio de decisión

Si lo que haces es mirar y reescribir la petición o la respuesta —normalizar el cache key, añadir cabeceras, redirigir, reescribir /docs a /docs/index.html, validar un JWT ya firmado— es CloudFront Functions: seis veces más barata, con free tier, y corre en todos los POPs. Salta a Lambda@Edge solo cuando necesites algo que Functions no puede hacer: llamar a otro servicio, leer el body, usar una librería, o engancharte al origin request (por ejemplo, para elegir origen dinámicamente). Ojo con la asimetría: Lambda@Edge no ve geolocalización en los triggers de viewer, y Functions no ve los triggers de origin.

Un tercer sabor reciente, Connection Functions, se ejecuta en el establecimiento de la conexión (antes de la petición HTTP). Mismos límites de 10 KB y 2 MB. No hace falta para nada de este curso.

Seguridad en el borde

  • Signed URLs vs signed cookies. Misma criptografía (clave privada tuya, clave pública en un key group asociado al behavior; RSA 2048 o ECDSA 256), distinto alcance. URL firmada para un fichero o cuando el cliente no soporta cookies (un instalador, un PDF). Cookie firmada para muchos ficheros sin cambiar las URLs (todos los segmentos de un vídeo HLS, el área de suscriptores). Si usas las dos, la URL firmada tiene prioridad. Política canned = solo caducidad; política custom = además fecha de inicio, rango de IPs y comodines en el recurso.
  • Geo restriction. Lista blanca o negra de países, resuelta en el borde por base de datos GeoIP. Barata y suficiente para cumplimiento de licencias; no es una medida antifraude (una VPN la salta).
  • AWS WAF. Se asocia la web ACL (scope CLOUDFRONT, creada en us-east-1) a la distribución y filtra antes de la caché. Servicio aparte, factura aparte.
  • Field-level encryption. Cifra hasta 10 campos concretos de un formulario con una clave pública tuya, de modo que ni tus propios servicios intermedios ven el número de tarjeta: solo el que tiene la privada. 0,02 USD por cada 10 000 peticiones. Nicho, pero conviene saber que existe.
  • mTLS de visitante (mutual authentication) con trust stores, y sus connection logs. Para APIs entre máquinas.
  • Origin failover. Un origin group declara un origen primario y uno secundario y una lista de códigos de estado (403, 404, 500, 502…) ante los cuales CloudFront reintenta contra el secundario. 10 grupos por distribución. Es lo que convierte dos buckets en dos regiones en un frontend con failover — sin Route 53 health checks.
  • HTTP/3 (QUIC). Se activa con http_version = "http2and3". Exige TLS 1.3 y SNI en el cliente, y soporta connection migration: el móvil que pasa de wifi a 5G no pierde la conexión. No cuesta nada activarlo.

La pregunta del cambio de free tier de 2025-07-15

El 15 de julio de 2025 AWS sustituyó el free tier clásico para cuentas nuevas: desaparecieron los 12 meses de prueba y las cuentas nuevas eligen entre un plan Free y uno Paid. Lo que no cambió es la categoría always free, y el 1 TB + 10 M peticiones de CloudFront está en ella: sigue siendo permanente, para cuentas viejas y nuevas. Sí hay una letra pequeña que conviene conocer: según la FAQ de CloudFront, ese free tier aplica solo al modo pay-as-you-go — si suscribes una distribución a un plan de tarifa plana, no se suman. Las cuentas creadas antes del 15 de julio de 2025 siguen con el free tier clásico.

La transferencia de S3 a CloudFront no se factura por ser S3 un origen AWS. El certificado de ACM es gratis. Route 53 sí cobra: 0,50 USD/mes por hosted zone. Total realista del proyecto 05: 0,50 USD/mes, todo de Route 53.

Lo que sí te arruinaría el presupuesto de 30 USD: una lista de Anycast static IPs (3 000 USD/mes), ssl_support_method = "vip" (600 USD/mes) o suscribirse al plan Business por curiosidad (200 USD/mes). Los tres son opt-in explícito; ninguno se activa solo.

El requisito famoso: el certificado va en us-east-1

Lo dice la documentación de ACM sin rodeos: «To use an ACM certificate with Amazon CloudFront, you must request or import the certificate in the US East (N. Virginia) region». No es una recomendación ni una optimización: si el ARN del certificado apunta a otra región, el apply falla.

El porqué no es arbitrario. Los certificados de ACM son recursos regionales que no se copian entre regiones, y CloudFront no vive en ninguna región: su plano de control está en us-east-1 y desde ahí distribuye el certificado a todos los POPs que la distribución use. Los servicios regionales (ALB, API Gateway regional) piden el certificado en su propia región, con la misma lógica.

Por eso el proyecto 05 enseña provider con alias

Tu bucket, tus tags y tu backend viven en la región que hayas elegido. El certificado tiene que vivir en otra. Un solo provider "aws" no puede estar en dos regiones a la vez: hace falta un segundo provider con alias, y pasárselo explícitamente a los recursos de ACM. Es la primera vez en el curso que un requisito de AWS obliga a una estructura concreta del código Terraform — no al revés.

HCLel patrón multi-región
provider "aws" {
  region = "eu-west-1"          # el provider por defecto: bucket, Route 53 records…
}

provider "aws" {
  alias  = "us_east_1"          # el segundo, solo para el certificado
  region = "us-east-1"
}

resource "aws_acm_certificate" "cdn" {
  provider          = aws.us_east_1   # ← sin esta línea, CloudFront lo rechaza
  domain_name       = "app.example.com"
  validation_method = "DNS"

  lifecycle { create_before_destroy = true }
}

Los detalles de validación, renovación y el trío acm_certificate + route53_record + acm_certificate_validation están en la ficha de ACM.

Cuándo NO usarlo

Úsalo si

  • Sirves contenido estático y quieres dominio propio con HTTPS.
  • Quieres que el origen deje de estar expuesto a internet.
  • Tu audiencia está repartida geográficamente.
  • Quieres WAF, geo restriction o TLS moderno sin tocar el origen.
  • Quieres que el origen deje de recibir el grueso del tráfico.

No lo uses si

  • Es una API dinámica, personalizada por usuario, sin nada cacheable, y todos tus usuarios están en la misma región que el origen.
  • Necesitas conexiones no HTTP (SSH, bases de datos, gRPC sin TLS).
  • El contenido cambia por petición y no puedes tolerar un solo byte obsoleto — piensa dos veces antes de desactivar la caché de una CDN.
La pregunta legítima: ¿aporta algo el borde a una API dinámica sin caché?

Menos de lo que parece, pero no cero. Lo que sí aporta aunque el hit ratio sea 0 %:

  • Terminación TLS en el borde. El handshake (varios round-trips) ocurre a 20 ms del usuario en vez de a 200 ms, y la conexión al origen se reutiliza keep-alive. Para un usuario lejano eso es real y medible.
  • Red troncal de AWS en lugar de peering público en el tramo largo.
  • Un solo sitio donde poner WAF, mTLS, geo restriction y política de TLS, y un origen que puede ser privado (VPC origin).
  • Absorción de DDoS por AWS Shield Standard, incluido.

Lo que no aporta: reducir carga del origen, ni latencia de la parte que sí computa. Y añade: una pieza más que desplegar, ~15 minutos por cambio, y la disciplina de decidir cache policy por ruta. El criterio: si tus usuarios están cerca del origen y no necesitas WAF ni ocultar el origen, la CDN delante de una API puramente dinámica es complejidad sin retorno. Si están lejos o quieres el origen privado, sí compensa aunque no cachee nada.

API Gateway edge-optimized Es CloudFront por debajo, pero gestionado por API Gateway y sin control sobre behaviors ni policies. Quieres un único servicio y no te importa perder el control fino de la caché.
Amplify Hosting Empaqueta S3 + CloudFront + CI/CD con dos clics. Quieres el resultado sin entender las piezas. Este curso quiere lo contrario.

En Terraform

HCLel patrón completo del proyecto 05
resource "aws_cloudfront_origin_access_control" "site" {
  name                              = "site-oac"
  origin_access_control_origin_type  = "s3"
  signing_behavior                   = "always"   # nunca "never"
  signing_protocol                   = "sigv4"
}

resource "aws_cloudfront_distribution" "site" {
  enabled             = true
  is_ipv6_enabled     = true
  default_root_object = "index.html"
  http_version        = "http2and3"
  price_class         = "PriceClass_All"
  aliases             = ["app.example.com"]

  origin {
    domain_name              = aws_s3_bucket.site.bucket_regional_domain_name
    origin_id                = "s3-site"
    origin_access_control_id = aws_cloudfront_origin_access_control.site.id
    # sin s3_origin_config: eso es OAI
  }

  default_cache_behavior {
    target_origin_id       = "s3-site"
    viewer_protocol_policy = "redirect-to-https"
    allowed_methods        = ["GET", "HEAD", "OPTIONS"]
    cached_methods         = ["GET", "HEAD"]
    compress               = true

    # managed CachingOptimized — nada de forwarded_values
    cache_policy_id = "658327ea-f89d-4fab-a63d-7e88639e58f6"
  }

  # SPA: cualquier ruta desconocida devuelve el index con 200
  custom_error_response {
    error_code            = 403
    response_code         = 200
    response_page_path    = "/index.html"
    error_caching_min_ttl = 0
  }

  viewer_certificate {
    acm_certificate_arn      = aws_acm_certificate_validation.cdn.certificate_arn
    ssl_support_method       = "sni-only"        # "vip" cuesta 600 USD/mes
    minimum_protocol_version = "TLSv1.2_2021"    # el default es TLSv1
  }

  restrictions {
    geo_restriction { restriction_type = "none" }
  }
}

resource "aws_s3_bucket_policy" "site" {
  bucket = aws_s3_bucket.site.id
  policy = data.aws_iam_policy_document.site.json
}

data "aws_iam_policy_document" "site" {
  statement {
    principals {
      type        = "Service"
      identifiers = ["cloudfront.amazonaws.com"]
    }
    actions   = ["s3:GetObject"]
    resources = ["${aws_s3_bucket.site.arn}/*"]

    condition {
      test     = "StringEquals"
      variable = "AWS:SourceArn"
      values   = [aws_cloudfront_distribution.site.arn]   # ← el cerrojo
    }
  }
}

Trampas conocidas, en orden de dolor:

  • Cada apply tarda ~15 minutos. El provider espera a que la distribución pase de InProgress a Deployed. Se puede desactivar con wait_for_deployment = false (útil en iteración), pero entonces el siguiente apply puede chocar con el despliegue en curso.
  • El destroy es peor. Hay que deshabilitar la distribución, esperar el despliegue, y solo entonces borrarla. Si tienes prisa, retain_on_delete = true la deja deshabilitada y te toca borrarla a mano después.
  • El ejemplo de la documentación del provider usa forwarded_values y OAI. Ambos están deprecados. Si copias de ahí, copias 2019.
  • minimum_protocol_version por defecto es TLSv1 — un protocolo que hoy no debería aceptar nada. Ponlo a TLSv1.2_2021 o superior siempre que uses certificado propio.
  • Usa bucket_regional_domain_name, no bucket_domain_name: el primero incluye la región y evita redirecciones 307 de S3 durante los primeros minutos de vida del bucket.
  • Los IDs de las managed policies son constantes globales. 658327ea-f89d-4fab-a63d-7e88639e58f6 es CachingOptimized en todas las cuentas. Aun así, el data "aws_cloudfront_cache_policy" { name = "Managed-CachingOptimized" } es más legible que pegar el UUID.
  • Una CloudFront Function se despliega en dos pasos: aws_cloudfront_function con publish = true, y luego function_association dentro del behavior. Sin el publish la distribución referencia una versión que no existe.
